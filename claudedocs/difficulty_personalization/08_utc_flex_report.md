# 08. 종류 수 ±1 유동 탐색 (v3) 보고

> 작성 2026-10-02 · 브랜치 `feature/pv-seed-variants` · 이전: [06 §8 재측정 v2](./06_p1_pilot_report.md)
> 사용자 결정: 플레이어가 크게 눈치채지 못할 범위에서 useTileCount ±1 허용. **쉬움 쪽은 utc0−1까지, 어려움 쪽은 utc0+1까지**(utc0 = 원맵 실제 종류 수). 봇·공유 코어는 수정하지 않는다.
> 재현성: ±1 풀 22개 × 64시드 = **1,408 run을 dotnet 골든과 대조해 불일치 0**(distVer `cs:191858cc9c06`, 잠정 = dotnet 기준). 모든 ±1 보드는 포트 strict(종류별 ÷3) 검사를 통과했다.
> W = 봇 가중 성공률(적응형 θ 2점 평균). **사람 클리어율이 아니다.**
> 기계 판독 결과: **`backend/data/pv_sandbox/pv_20261002_live3/selection_v3.json`**(레벨별 strict/relaxed, 토큰에 utc 포함, Δ·CI·눈치 지표).

## 0. 요약
1. **strict(기준 시드는 utc0만)**: 양방향 5시드 **19/30. v2와 같다.** ±1 풀을 써도 v2 미충족 5개(574·857·918·976·1148)는 하나도 살아나지 않았다. 이 레벨들은 원맵이 무작위 시드 거의 전부보다 쉬워서, 적응형 θ에서 utc0 기준 시드의 W가 이미 ≈0이다. utc0+1로도 "그보다 어려운" 쪽을 측정할 여지가 없다.
2. **relaxed(원맵 극단 레벨만 기준 시드 utc0∓1 허용)**: 극단 11레벨 중 **9개 확보**. 기준 시드가 원맵에 근접한다(|base−원맵| ≤0.065).
   - v2에서 확보했지만 기준이 원맵보다 0.24~0.47 어려웠던 5개(312·385·697·746·782)는 차이가 ≤0.06으로 줄었다.
   - v2 미충족 3개(574·976·1148)가 새로 확보됐다.
   - 857·918은 여전히 미충족(쉬움 쪽 유효 후보 1개뿐).
3. **정책별 최종 확보(30레벨 중)**:
   - strict: **19**. 그중 6개는 기준 시드가 원맵과 0.1 이상 다르다.
   - **극단 레벨만 relaxed: 22**. 22개 모두 기준 시드가 원맵 근접이다(극단 9개는 ≤0.065, 나머지 13개는 v2 strict 그대로).
   - 극단 레벨 제외(06 §8-4 a안): 13.
4. **±1 사용 분포**: strict에서는 **0개**(v2 ok 레벨의 결과 불변을 확인).
   - relaxed 9레벨: 원맵이 쉬운 쪽 극단 8개는 `b·e2·e1`이 utc0−1, 원맵이 어려운 쪽 극단 1개(95)는 `b·h1·h2`가 utc0+1이다.
   - 즉 **기준 시드와 같은 쪽 2칸이 ±1, 반대쪽 2칸은 utc0**인 형태다.
5. **눈치 지표**: −1이면 화면 종류 수가 1개 줄고 종류당 타일 수가 9~17% 늘어난다(예: 54타일 12→11종 = 4.5→4.9장/종). 같은 레벨 안에서 기준 시드와 쉬움 칸은 같은 종류 수라, 플레이어가 보는 차이는 "어려움 칸에서 종류가 1개 많아짐"뿐이다(§4).
6. **새 위험**: relaxed의 h2가 지나치게 어렵다(기준 대비 Δ −0.34~−0.61, W≈0인 경우가 많다). 원인은 선택 규칙의 far = 최대 Δ다. **h2를 목표 Δ(예 −0.25) 근접으로 고르는 상한 규칙**을 권고한다(§5).
7. **소요**: v3 추가분 53분(경합 상태). P2 반영 시 약 +7h(§6).
8. **"strict 시드가 v2와 다르다" 확인 결과(§8)**: v2 확보 19레벨 전부 **5시드가 같다(19/19)**. 의도하지 않은 변경은 없다. v3 스키마는 `tiers`에 기준 시드 `b`를 포함한 5칸이라 위치로 비교하면 어긋난다. 키로 비교해야 한다. export는 원자적 쓰기로 바꿨다.
9. **견고 선별(07 §5) 통합(§9)**: 안쪽 칸 Δ≥0.08 + 스킬 민감 제외를 v3 데이터로 사후 적용하면 정책 확보가 **22 → 11/30(상한)**으로 준다. 비용은 2단계 약 +95%, P2 약 30~40h. 대안으로 바깥 칸(e2·h2)만 견고 조건을 적용하는 안을 권고한다(재측정 필요).

## 5. 문제점·권고
1. **h2 과도 난도 (relaxed)**: Δ 최대 −0.61. h2 W가 574·976·1148·697·746에서 ≤0.003, 782 0.025, 312 0.047이다(봇이 사실상 못 깨는 수준). 이유는 기준 시드가 utc0−1로 쉬워졌는데 어려움 쪽은 utc0 시드라 바닥까지 떨어지기 때문이다.
   - 권고: 같은 쪽 far 칸을 **최대 Δ가 아니라 목표 Δ(예 쉬움 +0.20 / 어려움 −0.25)에 가장 가까운 유효 시드**로 고른다. 그리고 **최고 θ에서 W ≥ 0.05** 같은 하한을 데이터로 다시 정한다. 현 데이터만으로 재선별할 수 있다(추가 측정 불필요).
2. **857·918**: utc0−2가 허용되지 않아 쉬움 쪽을 채울 수 없다. 명시 맵 유지가 맞다.
3. **183 같은 반대쪽 극단**(원맵이 무작위보다 훨씬 어려움): 원맵 W가 0이라 봇으로는 기준 시드를 맞출 수 없다. 명시 맵 유지.
4. **결정 필요(사용자)**: 극단 레벨에 relaxed(기준 시드도 utc0±1) 적용 여부.
   - 적용: 22/30. 기준 난도는 원맵 근접이지만 화면 종류 수가 원맵보다 1개 적다.
   - 미적용: strict 19/30(기준 난도 상승 6개 포함) 또는 극단 제외 13/30.

## 7. 배포 형식 영향 (04 §A6-0에 반영)
- 토큰 확장안: `randSeed = "tok|tok|tok|tok|tok"`(순서 b|e2|e1|h1|h2), **tok = `seed` 또는 `seed@utc`**(`@` 없으면 레벨 useTileCount = utc0).
  - 예(574 relaxed): `1635606022@11|358522884@11|2079322438@11|894482049|264350516`
- 대안 비교:
  | 안 | 형식 | 장점 | 단점 |
  |---|---|---|---|
  | **A' (권고)** | `seed@utc` 토큰 | 필드 추가 없음, 사람이 읽을 수 있음, utc0 칸은 기존 A안과 동일 | 클라 파서에 `@` 처리 추가 |
  | B | `useTileCount`도 `"12\|11\|11\|12\|12"` 병렬 문자열 | 토큰 단순 | 두 필드 길이·순서가 어긋날 위험. GB가 useTileCount를 재계산·정수 처리(GB:425-451)하고, 에디터 다수 지점이 int로 처리 |
  | C | seed에 utc 인코딩(예 seed×16+utc) | 정수 1개 | 디버깅·검증이 어렵다. 시드 범위(2³¹) 침식 |
- 클라 파싱(A'): `^\d+(@\d+)?$` 토큰 1개 또는 5개, seed 1~2³¹−1, utc 1~15일 때만 사용한다. 아니면 첫 토큰(그 `@utc` 포함)만, 그것도 불량이면 기존 동작. 선택된 토큰의 utc를 그 판의 `ShuffleEmptyTiles` maxTileIndex로 쓴다(레벨 행의 useTileCount는 utc0 유지).
- 에디터 검사(`validate_a_v3`): 5토큰, (seed, utc) 쌍 서로 다름, |utc−utc0| ≤1, utc0에는 `@` 금지, 첫 토큰 = 선별 기준 시드. 정책상 추가: 쉬움 칸 utc ∈ {utc0−1, utc0}, 어려움 칸 ∈ {utc0, utc0+1}, 기준 칸은 strict면 utc0, relaxed면 utc0±1.

## 8. 확인 요청 — "strict 시드가 v2와 다르다"(594·662·676·1059 등)
- 결론 [사실]: **v3 strict의 5시드는 v2 확보 19레벨 전부 v2와 같다(19/19)**. 의도하지 않은 변경은 없고, 보정할 것도 없다.
- 근거:
  1. 최종 `selection_v3.json`(17:24)과 `selection_v2.json`(16:19)을 tier 키로 대조하면 차이가 0이다. A안 문자열도 19/19 같다.
  2. 검증 세션 입력(`verify/<lv>.json`의 `prep.seeds`) = v2 = v3 strict다. 594·662·676·1059도 같다.
  3. 16:40판도 같은 원천에서 나왔다. v3 strict는 `eval3/<lv>/strict.json`에서만 만들어지는데, 이 파일들은 16:28:22~16:28:55에 생성된 뒤 바뀐 적이 없다. 16:40 export와 17:24 export의 strict 값은 같다.
  4. 선별 로직상으로도 바뀔 수 없다. v2 ok 레벨은 utc0 후보만으로 양쪽이 채워지므로 ±1 풀을 만들지도 평가하지도 않는다. v3 쌍 선택(±1 최소 → 간격 최대)은 utc0만 있을 때 v2 규칙(최소 Δ 유효 = e1, 최대 Δ 유효 = e2)과 같은 쌍을 고른다. 재측정 난수도 쓰지 않았다(v2 2단계 데이터를 그대로 사용).
- 추정 원인(검증 세션 확인 필요): **스키마 차이로 인한 위치 비교 착오**로 보인다.
  - v2는 `base`가 따로 있고 `tiers`가 `e2·e1·h1·h2` 4칸이다.
  - v3는 `strict.tiers`가 **`b·e2·e1·h1·h2` 5칸**(기준 시드 포함)이다.
  - 위치 순서로 비교하면 한 칸씩 밀려 전부 다르게 보인다. **키(`b/e2/e1/h1/h2`)로 비교해야 한다.**
  - 또 하나의 가능성: export가 원자적 쓰기가 아니어서 쓰는 도중의 파일을 읽었을 수 있다. 다만 그 경우 JSON 파싱이 실패했을 것이다. 재발 방지로 두 export 스크립트를 임시 파일 → `os.replace` 원자적 쓰기로 바꿨다.
