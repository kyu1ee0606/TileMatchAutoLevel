## 1. 요약

1. [사실] 현재 32~1530 레벨은 에디터가 생성할 때 시드를 소비하고 **명시 타일 ID로 구워서** 배포한다(PD:376-449). 클라 `ShuffleEmptyTiles`는 t0에만 종류를 배정하므로(CS:880-903) 이 맵들에서는 randSeed·useTileCount를 바꿔도 **아무 효과가 없다**(01 §0-3, 02 §1).
2. [사실] 레벨 데이터는 **빌드에 내장**되어 있고 서버 델타 갱신은 꺼져 있다(01 §1). 변형을 배포하려면 앱을 업데이트해야 한다.
3. [사실] 에디터의 t0 분배 포트(TS·Python)는 **현 클라와 비트 단위로 다르다**. 클러스터 제거 셔플 누락, 구 알고리즘 사용, t0 순회 순서 차이가 원인이다(02 §2-2, 01 §9). 이 상태에서는 "클라가 시드로 배정하는" 원안을 검증할 수 없다.
4. [사실] 봇·MC 스윕은 규칙 정합성이 높은 상대 지표(B)로 쓸 수 있다. 솔버(A)는 bomb/curtain/frog/teleport/막힌 craft 레벨에서 신뢰할 수 없다(03 §1, §7).
5. [제안] **추천: 기존 맵을 기본형·폴백으로 그대로 두고, 같은 구조 위에서 "타입 배정만 다른 변형"을 에디터가 명시 타일로 구워 배포한다.** 클라는 검증된 후보 중 하나를 판 시작 전에 고른다. 변형 생성 방식은 **구조 인지 의도적 배정(대안 1)**을 주력으로 하고, useTileCount ±1은 그 안의 손잡이 하나로 둔다. 원안인 시드 추첨(대안 0/0')은 비교 대조군으로 남긴다.
6. [제안] 대안 1이 시드 추첨보다 **난도 차를 넓고 단조롭게** 만드는지는 2~3단계 실험으로 판정한다(§4-3). 판정 전에는 어느 쪽도 확정하지 않는다.
7. [제안] 첫 실험 후보는 32~1500 중 위험 기믹·craft·key·보스·샤드 불일치·count-only를 제외한 **537개**(에디터 LIVE 3차 배치 기준 스캔) 안에서 고른다(§7-3).
8. [제안] 결정이 필요한 질문은 15개다(§11). 핵심은 배포 경로(앱 업데이트 vs 델타 재활성화), 1~31 seed 0 정책, 용량 허용치다. 노트 간 불일치 8건은 부록 A에 정리했다.

## 3. 고정 타일 맵을 시드 생성형(t0화)으로 전환할 때의 위험

| # | 위험 | 근거 | 결과 |
|---|---|---|---|
| T1 | **원래 배치를 재현할 수 없다**: 생성기 RNG는 os.urandom으로 재시드되고, 원래 어느 칸이 t0였는지 기록이 없으며, bake 후 레벨 번호 시드로 relabel까지 거쳤다 | [사실] 02 §5-1 | t0화하면 기존 맵과 **다른 레벨**이 된다. 기존 검증 결과가 무효가 된다 |
| T2 | 분배 포트 비트 불일치 | [사실] TS 클러스터 셔플 누락(CS:1210-1217 vs TD:423-481), Py 구 알고리즘(BS:123-211), 에뮬 3/3 불일치(02 R1·R2), 클라 소비 순서 정밀판 01 §9-3 | 에디터가 검증한 보드 ≠ 플레이어 보드 |
| T3 | t0 순회 순서 | [사실] 클라 = 레이어 번호순 + 맵 JSON 키 삽입순(SimpleJSON Dictionary, 01 §9-1). GB 업로드가 키를 재정렬(GB:403). 에디터 저장본은 1424/1530이 다른 순서(02 R3). `layerIndex`는 map 키 등장순번(CS:548-553) | 같은 시드로도 배치 상이. 레이어 키 순서도 고정해야 함 |
| T4 | 음수·0 시드 처리 차이 | [사실] C#: 0만 시간 기반, 음수는 결정적(01 §2). TS/Py: `>0`이 아니면 시간 기반(TD:413, BS:309) | 0은 원천적으로 검증 불가. 음수 사용 금지 |
| T5 | 명시·t0 혼재 | [사실] toAdd 패딩이 명시 타입의 mod3을 t0로 먼저 채운다(CS:1123-1156, 1229-1236). TS는 baked inner·key를 카운트에서 누락(02 R4). TS만 총합 보정을 함(GE:408-478) | 혼재 레벨은 입력부터 다르게 해석된다 |
| T6 | 종류별 3의 배수 ≠ 풀이 가능 | [사실] ÷3 통과 LIVE 배치에서도 솔버 IMPOSSIBLE 18 / UNCERTAIN 24%(03 §1 night_study) | 변형마다 A·B 검증이 별도로 필요 |
| T7 | useTileCount 메타 불신 | [사실] 배포 메타와 실제 명시 종류 수가 57레벨에서 다르다(01 §2, 샤드 기준). GB가 "필드 명시 타입 수"로 재계산하면서 컨테이너 inner 전용 타입을 빠뜨린다(GB:425-451). 에디터 저장 기준으로는 32+ 121레벨이 다르고, 이 중 102개는 필드가 없다(02 §1-3) | "기본 종류 수" 정의를 실제 맵에서 다시 계산해야 한다 |
| T8 | visualTileSeed 혼동 | [사실] 비주얼 시드는 t0 출신 타일만 리맵하고(CS:1307-1354), 현재 전 레벨이 icon_order 스킨이라 리맵을 건너뛴다(CS:1312, 01 §2). 혼재 레벨에서는 매칭을 깨뜨릴 수 있다(02 §2-3) | **난도 수단이 아니다.** 변형 설계에서 제외하고 계약상 고정값으로 둔다 |
| T9 | 무시드 런타임 랜덤 기믹 | [사실] teleport `System.Random`, frog `UnityEngine.Random`, Shuffle 부스터 시간 기반(01 §5-4·5-5) | 변형을 고정해도 해당 기믹 레벨은 판마다 경로가 달라진다. 평가는 확률적으로 해야 한다 |

[제안] 결론: 기존 고정 맵을 t0화하지 않는다. 구조를 고정하고 타입 배정만 바꾼 **새 명시 변형을 추가**하며, 기존 맵은 variant `base`로 보존한다.

### 4-2. 추천 근거
- [사실] 클라가 t0를 배정하는 경로(0)는 T2~T5를 전부 해결하기 전까지 검증할 수 없다. 레벨은 빌드 내장이라 배포한 뒤 고칠 수도 없다(01 §1).
- [제안] 0'과 1은 "구운 명시 타입 배열"이라는 **같은 배포 계약**을 쓴다. 생성기만 갈아끼우면 되고, 계약·클라는 한 번만 만든다. 대안 0은 대조군으로 0' 형태로 실험한다(분포는 0과 같다).
- [제안] 종류±1은 정적 점수(종류>8에서만 ±2.67점, 03 §6)로도 실수 내성(V스윕 비단조, 03 §4-1)으로도 단조성 근거가 없다. 그래서 단독 손잡이로 쓰지 않는다.

### 4-3. 실험 설계: "1이 시드 추첨보다 난도 차를 넓고 단조롭게 만드는가"
| 항목 | 내용 [제안] |
|---|---|
| 대상 | §7-3 후보군에서 구간별 층화 표본(예: 구간 6개 × 5레벨 = 30레벨) |
| 처치 | (0') utc∈{b-1,b,b+1} × randSeed 5개 = 15후보 / (1) 노출 손잡이 수준 L∈{−2..+2} × 반복 3 (+ utc±1 조합 일부) |
| 측정 | MC 스윕 1-AUC·predicted_clear_rate의 **기본 맵 대비 Δ**(조기종료 off, CRN, 스킬점 3~8, 점당 ≥400판 목표 — 03 §4-2 Δ=0.1 검출 기준). 보조: 트레이 최대 점유·위기 빈도·실패 원인, 솔버 A |
| 판정 지표 | ① 폭: Δ 범위(최대−최소) ② 단조성: 손잡이 수준과 Δ의 Spearman ρ(레벨별 → 분포) ③ 잡음: 같은 수준 반복 간 Δ 표준편차 ④ 사용 가능 후보율: A 미확인·불가 비율 |
| 결정 규칙 | ①·②가 0'보다 크고 ③이 같거나 작으면 1 채택. 아니면 0'(시드 추첨 후 선별)로 간다. 수치 기준은 2단계 파일럿 분산 측정 후 확정 |
| 비용 | 03 §5 추정: 15후보 × 3점 × 400판 ≈ 레벨당 ~135s → 30레벨 ≈ 70분(8워커, 미검증) |

## 5. 추천 아키텍처와 배포 스키마

### 5-1. 흐름 [제안]
```
에디터: 기존 명시 맵(base) ─┬─ 구조 추출(위치·레이어·기믹·컨테이너 개수 고정) → structHash
                            ├─ 변형 생성기(대안 1 / 대조 0') → 명시 타입 배열 N개
                            ├─ 정합성(÷3·key·컨테이너) → 솔버 A → MC 스윕 B(Δ vs base, CI) → 분류 easy/base/hard
                            └─ 통과 변형만 → GB 변환(변형 필드 운반) → GameBoost → 게임 샤드 굽기 → 앱 빌드
클라: 판 시작 전 후보 선택(로컬 판단) → base map에 타입 배열 덮어쓰기 → typesHash 확인 → 불일치·누락 시 base
```

### 5-2. 정규화·해시 정의 [제안]
- **정규 순회 순서** = 클라 `GetEmptyTileList(true)`와 같다. 레이어 `layer_0..N` → 레이어 안은 **배포 JSON 키 순서(GB 정규화 후, 01 §9-1)** → 컨테이너는 그 위치에서 inner index 0(바닥)..n-1. 키 순서 자체를 계약의 일부로 고정한다.
- `structHash` = sha256(정규 순서대로 `(layerIdx, pos, effect, containerType, innerCount)` 직렬화, 타입 제외). **변형 유효성의 기준**이다.
- `typesHash` = sha256(정규 순서의 최종 타입 ID 배열, key 포함). 에디터·클라가 같은 값을 내야 한다.
- `genVer` = 변형 생성기 이름@버전, `evalVer` = 봇/솔버/스윕 코드 버전(커밋 해시 + 파라미터).

### 5-3. 스키마 초안 — 클라 배포 최소 필드 / 에디터 보관 메타 분리 [제안]
**클라 배포(레벨 행 또는 샤드 맵에 추가 — 위치는 §11 Q4)**
```json
{
  "id": "level_812",
  "map": { "layer": "4", "layer_0": { "col": "8", "row": "8", "tiles": { "1_1": ["t9",""], "2_5": ["craft_n","",[3,"t9_t8_t8"]] } } },
  "pv": {
    "v": 1,
    "structHash": "9f2c…e1",
    "base": { "tier": "base", "typesHash": "41aa…07" },
    "variants": [
      { "id": "e1", "tier": "easy", "types": "t9,t6,t2,…,t9,t8,t8", "typesHash": "c3d0…5b" },
      { "id": "h1", "tier": "hard", "types": "t9,t1,t2,…,t4,t8,t2", "typesHash": "7e11…a9" }
    ]
  }
}
```
- 고정 파라미터(위치·레이어·기믹·timea·트레이·보상·unlockTile)는 **레벨 공통값(기존 행·map)**에 한 번만 둔다. 변형에는 `types`만 넣는다.
- `types`는 정규 순서의 타입 ID 나열이다(컨테이너 inner 포함). 길이가 맞지 않거나 해시가 다르면 base로 간다.
- 대안 0(시드 구동)을 쓸 경우 `types` 대신 `{ "utc": 11, "seed": 384021, "distVer": "cs-2026-04-22" }`. 클라의 `distVer`가 다르면 base로 간다.
- `visualTileSeed`는 넣지 않는다(난도 수단이 아님, T8).

**에디터 보관 메타(배포 안 함, production 배치 meta 또는 별도 저장소)**
```json
{
  "level": 812, "variantId": "e1", "structHash": "9f2c…e1", "typesHash": "c3d0…5b",
  "genVer": "struct-assign@0.1", "genParams": { "exposureLevel": -2, "utc": 11, "rngSeed": 77123 },
  "baseRef": { "batch": "batch_1789636723287_uulknmtej", "typesHash": "41aa…07" },
  "checks": { "div3": true, "keySlots": "ok" },
  "solver": { "verdict": "PROVEN_SOLVABLE", "nodes": 412, "budget": "200000/8s", "evalVer": "solver@050abb1" },
  "sweep": { "evalVer": "mc@050abb1", "grid": [0.15,0.47,0.85], "gamesPerPoint": 400, "earlyTerm": false, "crnSeed": 4242,
             "auc1": 0.31, "deltaVsBase": -0.08, "deltaCI95": [-0.11,-0.05] },
  "dock": { "maxOccMean": 4.1, "crisisRate": 0.06, "failReasons": { "dock": 0.9, "chain": 0.1 } },
  "tier": "easy", "status": "validated", "validatedAt": "2026-10-xx"
}
```

### 5-4. 동일 입력 → 동일 논리 배치 검증 [제안]
1. **골든 벡터**: 정규화 JSON 입력 → 기대 typesHash/타입 배열. 클라는 Unity EditMode 테스트, 에디터는 pytest/vitest로 같은 값을 확인한다. 대안 0이면 zWellRandom 원시 출력(01 §3-6 seed별 값)과 분배 중간값까지 포함한다(02 §7).
2. **배포 전 전수 해시 대조**: 굽기 도구 결과를 헤드리스로 로드해 typesHash를 계산하고 에디터 값과 diff가 0인지 확인한다. 0이 아니면 빌드를 차단한다.
3. **런타임 자가검증**: 클라가 적용 직후 typesHash를 계산하고, 불일치하면 base + 오류 이벤트(침묵 금지, DESIGN_LEVEL_DATA_DELIVERY §7).

### 5-5. 평가 무효화 규칙 [제안]
| 변경 | 효과 |
|---|---|
| structHash 변경(맵 수정·재생성) | 해당 레벨 변형 **전부 폐기**하고 재생성 |
| base typesHash 변경 | Δ 기준이 바뀌므로 분류 재평가 |
| genVer 변경 | 기존 변형은 유지 가능(타입 배열 고정). 신규 생성분만 새 버전 |
| evalVer 변경(봇·솔버 규칙 수정) | status를 `stale`로 바꾸고 다음 빌드 전에 재평가. 미재평가 변형은 배포 제외 |
| (대안 0) distVer 변경 | 클라·에디터 버전이 다르면 해당 변형 비활성 |

- 조건: 레벨당 easy·hard가 각각 1개 이상일 때만 개인화 대상으로 쓴다.

### 9-1. 클라 개인화 원칙 (임계값 미확정) [제안]
- **입력 후보**: 최근 서로 다른 레벨의 첫 시도 성공 여부 / 부스터·부활 없이 클리어 / 같은 레벨 반복 실패 횟수 / (필요 시) 트레이 압박 지표(클라 계측 신설 필요).
