### Q1. 막힘 검사까지 vs MC 전 버전·A*까지 — 주간 호출 수 × 요청 절감 × 지원 비율, 그리고 다음 한 단계
**호출 수 실측 데이터는 맵툴에 없다**(요청 로그 파일 없음 — `backend/` 에 *.log 없음 ★). 대신 산출물 빈도로 하한을 잡는다.

### Q2. 어떤 증거가 모이면 `on` 으로 전환하나 — 코어 회귀와 호출처별 신규 검증의 경계
**경계**: 코어(규칙·정책·RNG)의 동일성은 기존 회귀(R2 140,400판·매 수 대조 4,568판·기준선 13세트, README)로 **재사용**한다. 호출처마다 새로 확인할 것은 "호출 계약" 4가지뿐 — ① 프로필·max_moves·seed 전달, ② 조기 종료 규칙, ③ 응답에 쓰이는 필드, ④ 장애·폴백 동작.

막힘 검사 경로 `on` 기준(전부 충족):
1. **판 단위 정확 일치(분포 검정 아님)** — 고정 입력 회귀: 생산 레벨 ≥300개(기믹·크기 층화) × 막힘 검사 실제 호출 형태(5판, `_fix_same_type_blocking` 시드 50×3판) × 명시 RNG 상태 → 판별 cleared·moves **100% 일치**, 그리고 호출처 최종 결정(`has_deadlock`, 채택 randSeed, 최종 레벨 JSON) **100% 일치**.
2. **seed=None 처리**: 판 시작 전 파이썬 `self._rng.getstate()` 를 그대로 넘기는 방식이면 **기존 RNG 흐름과 같다**(B 가 우려한 "명시 시드는 의미가 다를 수 있다"는 *새 시드 부여* 방식에만 해당, 상태 전달은 같은 MT 상태에서 시작). C# `PyRandom` 은 getstate/setstate 지원(README 구성 표). 단 t0+randSeed≤0(`time.time()` 시드)은 여전히 재현 불가 → unsupported 로 파이썬 처리. → shadow 실요청에서도 `skip_seed_none` 이 사라지고 **비교 분모 = 실요청 전체 − unsupported**.
3. **분모 공개**: shadow 표본에서 비교 성공 ≥95%, unsupported·queue drop·오류 비율을 따로 기록(B 위험 1 수용). 응답 필드: 이 경로는 `clear_rate`·`avg_moves`(failure_reason 문구, `generator.py:16428-16434`)만 쓰므로 판별 moves 로 재계산 가능 — combo/tiles_cleared 불필요.
4. **요청 단위 속도**: 유휴 단독(load ≤ 코어 수)에서 generate() p50 ≥5×, p95 악화 없음, IPC 왕복 p95 측정값 기록.
5. **장애 시험**: 워커 kill·타임아웃·버전 불일치 각각에서 파이썬 폴백으로 같은 결과, 대기 요청 유실 0, 폴백 발생 시 로그·카운터.
6. shadow 기간은 달력(2주)이 아니라 **건수**로: 실요청 비교 ≥500호출 또는 생산 배치 1개 분량, 둘 중 먼저.

autoplay 등 통계 필드를 쓰는 경로(B 지적: avg/min/max moves, combo, std — `analyze.py:581-592`)는 C# 출력에 combo·tiles_cleared 가 없으므로(조사 §1-2) **출력 확장 전에는 `on` 불가**. 동의.

## 2. B 주장 구분

### 동의
- **B4 통계 산술**: 50% 성공률·각 300판 차이 95% 반폭 ≈ 8.0%p, 1,000판 ≈ 4.4%p 는 맞다(1.96·√(0.5/300)=0.080). 계획 §0-A 3 의 "±3%p, ≥300판"은 성립하지 않는 기준. → 분포 검정을 게이트로 쓰지 말고 판 단위 정확 일치로 가야 한다는 내 주장(위 Q2-2)을 강화하는 근거.
- **B4 응답 필드**: 현 shadow 는 cleared 비트열만 비교(`tilecore_bot.py:185-214`). autoplay 응답 동일성 미보증 — 동의.
- **B3 버전·출처 고정 우선**: 새 사실 0-3(DDA 실사용 경로가 개발 스냅샷)으로 실례 확인. `~/tilecore` git 화 + 릴리스 해시 + 시작 시 버전 확인은 **serve 보다 먼저** 하는 것이 맞다(작업량 작음 [추정 0.5 인일]).
- **B5 범위 축소·자동 확장 금지**, **"중단은 부채 삭제가 아니다"**: 동의.
- **B1 AI 개발 속도 보정**: 1차 구현 1일 남짓(PLAN §8 진행 11-02) — 인일 추정이 구현엔 과대, 검토·운영엔 과소일 수 있다는 지적 동의.

### 반박
- **B3 "폴백은 용량 설계 대상, 폴백 시 지연 급증"**: 폴백의 최악 = 오늘 파이썬 성능 그대로다. 문제는 C# 처리량을 믿고 **요청량을 늘린 뒤**에만 생긴다. 지금 맵툴은 요청량이 C# 전제로 바뀔 계획이 없고 배치 빈도도 낮음(0-1). → 폴백 동시 수 제한은 기존 풀 크기(gen_pool ≤8, `generate.py:28`) 그대로 두면 충분. 별도 용량 설계는 과잉 [추정].
- **B3 "지원 기능 협상·요청 ID·취소…" 전체를 첫 완료 기준으로**: 요청 ID·타임아웃·EOF 재시작·버전 확인은 필수. 그러나 기능 협상·취소 프로토콜까지 선행하면 serve 가 첫 사용자 가치 없이 커진다. 미지원은 이미 `unsupported` 응답으로 처리되므로 협상 없이도 안전 [사실: README 미지원 절 — 거절 → 파이썬]. 최소 계약으로 시작 권고.
- **B4 "seed=None 은 별도 분포 검증으로 유지"**: 위 Q2-2 대로 RNG 상태 전달이면 분포 검증 불필요. B 의 산술이 보여주듯 분포 검정은 판수가 수천이어야 의미 → 비싸고 약함. 상태 전달 구현이 막히는 경우에만 분포 검증으로 후퇴.
- **B 대안표 "Python만 최적화 = 정본 1벌로 가장 단순"**: 정본 파이썬 코드를 고치면 **기존 결과와의 동일성 검증이 똑같이 필요**(덮임·복사 경로 변경 = 같은 회귀 부담). 단순한 건 맞지만 "검증 비용 0"은 아니고 기대 배수 1.7~3×(1라운드 Amdahl). 다만 B 가 별도로 든 "계산량 축소"는 아래처럼 동의 범위가 있음.

### 근거 부족

## 3. 합의점 / 남는 쟁점

**합의**
1. C# 봇 코어는 유지(성능 27~59× 입증, 동일성 14만 판). 처음부터 다른 기술로 갈 근거 없음.
2. 다음 확정 범위 = 버전 고정 → 상주 워커+어댑터 → 생성기 막힘 검사. 이후 확장은 사용량 근거로 재결정. MC 전 버전·A* 자동 약속 안 함.
3. 계획 §0-A 3 의 분포 동등 기준(±3%p·≥300판)은 통계적으로 부적합 → 재정의 필요.
4. "불일치 0"은 비교된 분모에 대해서만 말한다. skip·unsupported·drop 비율 공개.
5. 통계 필드를 쓰는 경로는 출력 확장 전 `on` 불가.

**남는 쟁점**
1. **seed=None 동일성 방식**: A = MT 상태 전달로 판 단위 정확 일치 / B = 회귀는 명시 시드, 실경로는 분포 검증. (판정 방법: 상태 전달 시험 구현 1회로 결론 — 반나절 [추정])
2. **계산량 축소(조기 중단)를 파이썬에 지금 적용할지**: A = 막힘 검사 "2판 클리어 또는 4판 실패 시 중단"은 통과/실패 결정이 수학적으로 동일(5판 중 ≥2 클리어 규칙, `generator.py:16419-16428`)하므로 편향 없음 / B = 조기 종료는 통계 편향 검증 비용. 차이점: B 의 우려는 *클리어율 추정*에 해당, 이 경로는 *임계 결정*이라 해당 없음. 단 보고 `clear_rate` 값과 `_ensure_no_deadlock` 의 best 추적값이 바뀌므로 정본 파이썬 동작 변경 = **사용자 결정 사항**(PLAN §8-4 정신).
3. **serve 첫 완료 기준의 두께**: A 최소 계약 / B 협상·취소·용량까지.
4. **생성기 단계의 경제성**: 0-1 사실로 주간 CPU 절감은 작다. A 는 "검증된 프로필만 쓰는 가장 싼 실전 시험대 + 단건 대기 개선"으로 진행 지지, B 도 진행 지지하나 근거는 다름 — 합의는 됐지만 **기대치는 낮게** 잡아야 함.

### 하지 말 것
- **BS 규칙 A* solver 구현 착수** — 수요(study·batch-verify 실패 경로 빈도)와 판정 확정률 가치 측정 전엔 금지. FastJudge shadow 결과를 서비스 판정으로 쓰는 것도 금지(규칙 다름, `tilecore_shadow.py:7-10`).
- **MC v1~v2.3 정책 이식** — 서비스 기본 v1 은 파이썬으로도 점당 수 초 이내. 사용 근거 없이 착수 금지.
- **분포 검정(±3%p·≥300판)을 동일성 게이트로 쓰기** — 통계적으로 부적합(B 산술).
- **개발 스냅샷 dll 을 실사용 경로에 두기**(현 DDA 야간) — 1단계에서 정리.
- **요청당 CLI 방식으로 생성기 경로 `on`** — 기동 0.1 s × 호출 10~58회로 이득 1.6~3× 에 그침(1라운드 표).
- **파이썬 정본 제거 논의** — 미지원 프로필·통계 필드·상태 단위 API 가 남아 있어 시기상조(B2 동의).
- **C# 다중 스레드 수를 크게 잡기** — 바쁜 기계에서 8스레드 벽 1.4~2.2×(README 측정 2), 2~4 스레드면 충분.

### 한계
- 사용량은 생산 배치 파일 수로만 추정(요청 로그 없음). 단건 UI 생성 빈도 미상.
- 요청 단위 지연·IPC 비용은 여전히 미측정 — 2단계 통과 기준에 넣음.
- `night_common.py` 는 기본값만 확인, 실제 야간 실행이 환경변수로 다른 dll 을 지정했는지는 미확인.
