# 백엔드 최적화 정적 리뷰

대상: `479f8fb`, `1721110`. 줄 번호는 최종 `1721110` 기준. Git 객체만 읽었으며 서버 실행, 요청 전송, 부하·경쟁·파일시스템 실험은 하지 않았다. 시나리오는 코드에서 도출한 실행 순서다.

## 지적

1. **높음 — 인덱스의 잘못 결합된 버전을 신뢰하면 409 검사가 무력화된다.** `backend/app/api/routes/production_store.py:449-451` (신규 신뢰 경로), `:75-83,572,580`. A가 v2 파일을 replace한 뒤 인덱스 갱신 전에 멈춤 → B는 파일에서 v2를 읽고 v3를 저장·인덱스 갱신 → A 재개 시 `_index_entry`가 현재 v3 파일의 stat과 A의 v2 인자를 결합해 인덱스에 저장한다. 이후 실제 파일은 v3인데 `(mtime,size)`가 일치하는 인덱스 v2를 신뢰하므로 base_version=2 요청이 승인되고 v3를 덮어쓴다. 시간 정밀도 충돌 없이 가능한 경로다. 기존 인덱스 생성 경쟁이 이번 변경으로 쓰기 승인까지 영향을 주게 됐다. 배치별 교차 프로세스 잠금으로 버전 검사부터 파일·인덱스 갱신까지 보호하거나 버전의 권위는 실제 문서에 유지해야 한다. 기존 동시 PUT 자체의 비원자적 검사와는 구분된다.

2. **높음 — 등껍질 측정의 스레드 전환 후 저장 경쟁을 보호하지 않았다.** `backend/app/api/routes/analyze.py:1948,1998`; `backend/app/core/turtle_bases.py:147-181`. measure는 이제 worker thread에서 `TB.set_difficulty`를 실행하지만 이 함수와 put_base/delete_base는 모두 잠금 없는 전체 파일 read-modify-write다. 측정 A가 파일을 읽음 → 다른 요청이 B 항목을 수정/삭제하고 저장 → 측정 A가 옛 파일에 난이도만 붙여 저장하면 B 변경 유실/삭제 항목 부활. 기존 단일 프로세스의 await 없는 async 경로끼리는 직렬이었으나 이제 겹친다. 동일 저장소의 모든 쓰기 경로를 같은 잠금으로 보호해야 한다.

3. **중간 — 보스 생성의 전역 random.seed가 동시 요청 간 결정성을 깨뜨린다.** `backend/app/api/routes/analyze.py:2434,2483,2519`. def 전환 뒤 A가 seed(A)를 설정하고 B가 seed(B)를 설정하면 A의 폭탄 카운트·기믹 배치가 B의 난수 상태를 소비한다. 같은 레벨/seed의 미리보기와 실제 생성이 다른 결과를 낼 수 있다. 요청별 Random을 하위 생성 함수까지 전달해야 한다. 일반 from-template의 직접 색 선택은 `:3124,3146`에서 로컬 Random을 사용한다.

4. **중간 — 측정 중 편집된 템플릿에 옛 모양의 점수를 저장한다.** `backend/app/api/routes/analyze.py:3274-3288`. A가 기존 level_json으로 긴 측정을 하는 동안 B가 같은 template_id의 레이어를 수정하거나 삭제 후 같은 ID로 재생성 → A는 최신 entry의 존재만 확인하고 옛 결과를 병합한다. 최신 모양은 보존되지만 measured_difficulty 등은 다른 모양의 값이다. `:3249-3266`에서 읽은 내용/세대와 저장 시 최신본을 비교해 달라졌으면 결과를 버리거나 재측정해야 한다.

## 잠금·캐시 및 기존 한계

- level_templates 저장 호출 검색 결과 6곳(`analyze.py:2894,2921,3043,3288,3336,3353`)은 최종 커밋에서 모두 전체 read-modify-write 잠금 또는 measure의 명시적 잠금 아래에 있다. `backend/app`의 해당 파일명/저장 함수 검색에서 별도 쓰기 엔드포인트는 발견하지 못했다. scripts나 외부 프로세스 전체에 대한 보장은 아니다.
- RLock을 같은 스레드에서 데코레이터 → load/save로 재진입하므로 이 경로 자체의 재진입 교착은 발견하지 못했다. measure의 봇 계산은 잠금 밖이다.
- **높음, 기존 운영 한계 — RLock은 프로세스 사이를 보호하지 않는다.** `analyze.py:2749`; `run.sh:19-21`의 backend-prod는 기본 workers=4다. 다른 워커에서 서로 다른 템플릿을 동시에 수정하면 각자 전체 사본을 저장해 한쪽 변경이 유실될 수 있다. 기존 다중 워커 경쟁을 이번 잠금이 해결한 것으로 간주하면 안 된다. 단일 워커 dev-watch와 구분된다.
- 캐시는 `(st_mtime_ns,st_size)`를 비교하고 pickle.loads로 독립 사본을 돌려준다(`analyze.py:2764-2771`). 같은 초에 두 번 저장했다고 같은 mtime_ns가 되는 것은 아니다. 파일시스템 해상도/시간 보존 교체 등으로 두 값이 실제 같으면 stale hit 가능하고 `_save_level_templates:2777`에서 명시적으로 캐시를 무효화하지 않는다. 이 환경에서 충돌이 발생하는지는 미검증이며 확정 재현으로 보고하지 않는다. 저장 성공 시 캐시를 비우면 동일 프로세스 경로는 방어 가능하다.
- `production_store.py:509-512`: 인덱스 미스 때 이미 읽은 문서를 재사용하고, 히트 때 partial 병합용으로 한 번 읽는다. 인덱스 일치만으로 버전을 신뢰하는 안전성은 지적 1과 별개다.
- analyze의 공유 LevelAnalyzer에서 self 필드 대입 검색은 일치 없음. 해당 검색만으로 모든 하위 라이브러리의 스레드 안전성을 증명하지는 않았다.
- `scripts/dev-watch.sh:22`의 reload-exclude 추가를 확인했다. 설치된 uvicorn/watchfiles 구현과 실제 폴링 CPU는 읽거나 실행하지 않아, 저장 파일을 재로드 대상에서 빼는 것과 디렉터리 스캔 비용 감소가 같은 효과인지는 미검증이다.

### 기존 지적 해소 범위

- **지적 1 해소:** `production_store.py:439`에서 인덱스 단축을 제거해 실제 문서 버전을 사용한다. `:482-485`는 같은 프로세스의 동일 배치 PUT을 검사부터 인덱스 저장까지 직렬화한다. 다중 워커 간 동시 PUT은 여전히 보호하지 못한다. DELETE(`:671-678`)도 이 잠금을 사용하지 않아 PUT 중 삭제 후 PUT의 replace로 부활할 수 있다. 이 두 한계는 기존부터 존재했고 이번 수정으로 해결된 것은 아니다.
- **지적 2 단일 프로세스에서 해소:** `turtle_bases.py:161,182,192`의 put/delete/set_difficulty가 같은 RLock을 사용한다. 타 항목 변경 유실·삭제 부활 시나리오는 해당 프로세스에서 직렬화된다. 다중 프로세스 한계는 유지된다.
- **지적 3 부분 해소:** 보스 요청끼리는 `_BOSS_GEN_LOCK`으로 직렬화되지만 다른 전역 난수 소비자는 보호하지 않는다(아래 잔존 지적).
- **지적 4 단일 프로세스에서 해소:** 측정 전 지문(`analyze.py:3277`)과 잠금 안 최신본 지문(`:3300`)을 비교한다. 모양 변경/다른 모양으로 재생성되면 저장하지 않는다. 기존 파일 캐시 서명 충돌과 다중 워커 잠금 한계는 별개로 남는다.

### 새 지적 및 불완전한 보완

1. **중간, 신규 응답 호환 문제 — base_changed를 성공으로 표시.** `analyze.py:1998-2000`은 HTTP 200에 `{ok:false,error:'base_changed'}`를 반환하지만 `frontend/src/components/TurtleBaseLibrary.tsx:153-155`는 ok/error를 확인하지 않고 항상 '측정 완료 — coef undefined'를 표시한다. 다른 탭에서 측정 중 모양을 수정/삭제하면 서버는 결과를 버려도 UI는 성공으로 안내한다. 응답을 판별하고 message를 보여줘야 한다. 반면 `PatternDebugPanel.tsx:584,633`은 error를 확인하므로 template_changed를 실패로 처리한다(한국어 message 대신 오류 코드만 표시).

2. **중간, 잔존 — 보스 전용 잠금으로 전역 random을 격리할 수 없다.** `analyze.py:2442,2495`와 `:4060,4149`. `/debug/test-level` 역시 def 스레드풀 경로이며 보스 잠금 없이 random.shuffle을 호출한다. 보스가 seed를 설정한 뒤 테스트 레벨 요청이 shuffle하면 이후 보스 난수열이 달라진다. 추가 테스트는 보스 요청끼리만 비교하므로 이 경우를 검사하지 않는다. 요청별 Random을 전달하는 방식이 필요하다.

3. **중간, 가드 누락 — expect_cells는 grid 변경을 놓친다.** `turtle_bases.py:200`, `analyze.py:1967-1969,1998`. 측정 중 cells를 유지하고 grid만 바꾸면 검사에 통과해 옛 격자의 점수가 새 격자에 저장된다. `generator.py:1596-1606`은 base_col로 레이어 크기·침식 범위/오프셋을 계산하므로 grid도 측정 입력이다. grid와 cells를 함께 비교해야 한다. 동일 ID 삭제 후 재생성에 대한 세대 식별도 없다.

4. **낮음, 신규 누적 — 배치별 잠금 dict가 정리되지 않는다.** `production_store.py:473,483`. 정상 저장뿐 아니라 존재하지 않는 새 ID에 partial PUT하여 409가 발생해도 lock이 남는다. 서로 다른 ID를 계속 요청하거나 배치를 생성·삭제하면 프로세스 수명 동안 키와 lock 수가 증가한다. 상한/안전한 수명 관리가 필요하며, 대기자가 있는 lock을 단순 삭제하면 직렬화가 깨지므로 주의해야 한다.

### 잠금·예외 확인

- `_BATCH_LOCKS_GUARD`는 배치 lock을 기다리기 전에 해제한다. 확인한 경로에는 역순 재획득이나 같은 non-reentrant Lock의 재진입이 없다. LT/TB의 내부 load/save 재진입에는 RLock이 사용된다. 모든 신규 획득은 with 문이므로 HTTPException/일반 예외에서도 해제된다. 교착을 실제 실행으로 검증한 것은 아니다.
- 배치 lock 안에는 파일 파싱·규칙 게이트·덤프가 들어가므로 같은 배치 요청은 그 시간만큼 대기한다. 보스 lock은 조립·후처리·정적 분석까지 포함하여 보스 요청 전체를 직렬화한다(`analyze.py:2442-2723`). 봇 장시간 측정은 LT/TB lock 밖이며 put_base의 compute_turtle_meta는 TB lock 안이다(`turtle_bases.py:172`). async turtle save/delete가 TB lock을 기다리면 이벤트 루프를 잠깐 막을 수 있다. 실제 대기 시간/부하 영향은 미측정이다.
- 추가 `backend/tests/test_backend_concurrency.py`는 인덱스 오염, 같은 base 동시 PUT, turtle 쓰기/삭제, 보스끼리 동시 생성, 템플릿 모양 변경을 검사하도록 작성되어 있다. 실행하지 않았으므로 통과로 보고하지 않는다. 다중 프로세스, 보스와 타 API 난수 교차, grid만 변경, base_changed UI는 포함되지 않는다.
