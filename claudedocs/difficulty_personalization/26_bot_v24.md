## 2. 텔레포트·개구리 연출 후 선택
**게임**:
- 텔레포트: 사용자 클릭 3번째마다(`ClickCount % 3 == 0`, 냥이 수집 중 클릭은 안 셈 G TileGroup.cs:1990-1998). 텔레포트 타일만 `onTeleport=true`로 0.5 s 잠금(:2044-2048, TileEffect.cs:1099) — 보드 전체 잠금이 아니다. 타입 데이터·스프라이트는 +0.5 s 에 함께 바뀐다(`DOVirtual.DelayedCall(0.5f)` :2051, `ChangeTileType`). 잠금 중 다른 타일을 클릭하면 그 클릭이 독에 들어간 뒤 대기 중 회전을 즉시 완료(:2026-2031). 순서: 독 추가·매칭·실패 판정(Dock.cs:1023, 1153) → `AddClickCount`(GameController.cs:2955) → 개구리(:2958).
- 개구리: 실제 코드는 `FrogManager.MoveAllFrog`(TileGroup.MoveFrog 는 호출 안 됨). 클릭마다 마지막 단계, 목적지와 `onFrog` 플래그는 클릭 시점에 즉시 확정(FrogManager.cs:59, 182-187), 점프 0.5 s. **점프 중 클릭은 막히지 않는다**. 대신 점프 중 들어온 클릭에는 개구리가 다시 뛰지 않는다(`isFrogMoving` 조기 반환 :16). 19 문서 #20 의 "점프 중 클릭 생략"은 "점프 중 클릭 시 개구리 이동 생략"으로 정정한다.

**봇**: `_play_game` 은 수 선택 → `_apply_move`(매칭) → `_process_move_effects`(폭탄 → 개구리 → 커튼 → 텔레포트 → craft 배출) → 다음 턴 선택. 다음 턴 점수는 바뀐 보드(타입·`on_frog`)로 매번 새로 계산한다. 캐시(`_accessible_type_counts`)는 `_apply_move` 에서 무효화되고, 텔레포트·개구리 효과 처리 중 다시 계산되는 경로가 없다 — 텔레포트 12·개구리 12레벨 × 8판 실측에서 효과 처리 직후 캐시가 채워져 있던 경우 0회(오래된 타입으로 고를 수 없음). 같은 턴 연속 선택 경로도 없다(1클릭 = 1선택; 냥이 수집 픽은 선택이 아님). 봇의 선읽기는 텔레포트를 예측하지 않는다(사람도 무작위 순환은 예측 불가).
**판정: 봇은 이미 "이동 완료 후 보드 기준으로만 선택"한다. 수정 없음.** 남는 차이는 시간 의존(빠른 연속 클릭 시 개구리 이동 생략·텔레포트 잠금 중 다른 타일 클릭)이며 수 단위 봇에는 넣지 않았다.

## 3. 냥이의 도움 — savvy / naive
**게임 확인(19 §4 의 미확인 세부)**:
- (a) 사이클 수 제한 **없음**. `autoCollectCount` 는 1~3 이면 켜기만 한다(LevelController.cs:138-139, 1340-1352). 뱃지 수는 프리팹 `badgeCount: 3`(AutoCollectController.cs:43, `@Game - 게임화면.prefab`). 사이클은 클리어·실패·필드 소진까지 반복(:807-811, :1090, :1297, :1310-1314). 프리팹 타이밍: `cycleDelay 0.5`, `collectingEntryDelay 0.4`, `firstThrowArrivalDelay 0.85`, `lastRoundCleanupDelay 2`.
- (b) 첫 사이클은 스폰 애니 종료 후, 이후 사이클은 수집 단계 뒤 독이 빌 때(`OnDockEmpty` :621-631). 뱃지 3장은 덮임 무관 필드 타일, 같은 타입 ≤2(:1668-1713).
- (c) 뱃지는 독 칸을 차지하고 넘침 판정에 포함된다(Dock.cs:3626, 2576-2581).
- (d) 수집 = **모든** 뱃지가 매칭된 순간(:549-564), 이번 사이클 가상버퍼의 타입별 잔여 r 마다 3−r 장을 필드에서(TileList 순서, 덮임 무관) 채운다(:973-987, FindTilesInField :1539-1555). → 독에 미완성 타입이 많을 때 마지막 뱃지를 맞추면 이득이다. v2.3 `auto_collect` 구현과 같은 알고리즘이다(19 §4 원인 후보 (a) 기각).

**구현** (`ac_policy`, B `_v24_savvy_select`): 판마다 savvy 여부를 `p_savvy` 로 추첨. savvy 는 마지막 뱃지를 끝내는 수(트리거)가 보이면 독이 (잠기지 않은 칸 − 1)까지 찰 때까지 미루고, 그동안 독에 없는 새 타입(완성 시 2장 무료)을 우선 집는다. 트리거가 안 보이면 평소대로. naive = v2.3 동작.

**적합(41레벨, 128판, θ 0.65/0.85/1.0, 혼합 = p·savvy + (1−p)·naive)**:

| θ | naive | savvy | AF mid | p 최적(절대) | MAE naive → 최적 | 2겹 CV MAE naive / 최적 | 구간별 p (32~100/101~300/301~500) |
|---|---|---|---|---|---|---|---|
| 0.65 | 0.136 | 0.112 | 0.677 | 0.00 | 0.541 → 0.541 | 0.540 / 0.540 | 0 / 0 / 0 |
| 0.85 | 0.303 | 0.282 | 0.677 | 0.00 | 0.375 → 0.375 | 0.374 / 0.376 | 0 / 0 / 1 |
| 1.0 | 0.451 | 0.461 | 0.677 | 0.45 | 0.234 → 0.226 | 0.233 / 0.233 | 0 / 0.4 / 1 |

- savvy 정책은 봇 성공률을 거의 바꾸지 못한다(θ1.0 +0.010, θ0.65 −0.025). 실패의 대부분이 트리거와 무관한 독 넘침(Normal)이라 마지막 뱃지 타이밍으로 얻는 무료 타일이 결과를 바꾸지 못한다. p_savvy 는 CV 로 **식별되지 않는다**(최적 p 의 CV MAE = naive). 기본값은 θ1.0 전체 적합 0.45 로 두되 의미 있는 추정치가 아니다.

1. 그 항목을 빼면 E1 MAE 가 **반복 sd(4반복) 2배 이상 나빠지거나**, MAE 동률(차이 < 2 sd)이면서 ρ 가 0.01 이상 나빠지고 MAE 악화가 없을 때 → **채택**.

3. 빼면 오히려 MAE 가 2 sd 이상 좋아짐 → **기각**.
4. 허용 악화: 채택 항목이라도 기믹별 E1 MAE 가 v2.3 대비 0.01(1%p) 넘게 나빠지는 기믹이 생기면 보고에 명시하고, 0.02 넘으면 보류로 내린다.
5. 목표 대신 unaided 하한·상한 각각을 목표로 해도 결론(채택/보류)이 바뀌면 → **보류**.
