## 2. 공통 항목

### C1. 독 관리
- **게임 [UI]**: 7칸(`Dock.cs:569`). 빈 칸이 ≤2(`_bufferDangerThreshold=2`, 게임화면 프리팹 :10334)면 독 전체가 1초 2회 1.12배 맥동(Dock.cs:85, 1197-1204, 1370-1389). 곧 매칭될 타일은 점유로 안 셈 → **실질 5칸 점유부터 경고**. 색·문구 없음. 잠긴 칸은 자물쇠 그림(DockSlot.cs:274-292).
- **사람**: 숙련자는 경고 전부터(4~5칸) 새 타입을 피한다 [추정]. 초보는 경고를 보고서야 반응하거나 경고 뒤에 서두르다 실수한다 [추정]. AF 실패 판 combo_max p50 3~5 vs 클리어 8 [AF] — 실패 판은 연쇄가 짧다(독을 비우지 못하고 쌓음).
- **봇**: 비매치 수 감점 독 ≥4 −5·ba·(1.5−rt), ≥5 −20·(1.5−rt), ≥6 −50·(1.5−rt)(B:3081-3087). 선읽기 예상 독 ≥4/5/6 −5/−20/−40(B:6020-6029). 매치되는 수가 있으면 무조건 매치 우선(B:4720-4723). 패닉(B:4549-4586): 모든 θ 프로파일이 `bot_type=AVERAGE`(MC:132) → 임계 4, 독 ≥4 에서 실수율 최대 ×(1+…)·선읽기 깊이 감소(깊이는 어차피 on/off만 의미, C2).
- **판정: 부분 일치.** 임계 위치(5칸)는 사람 경고와 비슷하다. 차이 두 가지: (a) 임계가 **7칸 기준 절대값**이라 잠긴 칸·냥이 뱃지가 있을 때 한 칸 늦다(→ key 절). (b) 패닉은 "독이 차면 실수 증가"인데, 게임은 그 시점에 경고를 띄운다 — 사람은 경고 후 오히려 신중해질 수도 있다 [추정].
- **잔차 방향**: (a)는 봇을 더 약하게 → 잠긴 칸 레벨 음수 잔차와 같은 방향. (b)는 미정.
- **제안**: 독 감점 임계를 `unlocked_slots` 기준 상대값으로(아래 key 절, 상). 패닉 방향은 기획 질문 Q1 후 결정(하).

### C2. 앞수 읽기 깊이
- **봇 실제**: `lookahead_depth = round(5θ)`(MC:33)지만 유효한 `_estimate_future_score`(B:5940, 같은 이름 앞 정의 B:5575 는 덮여 쓰이지 않음)는 `depth` 를 **쓰지 않는 1수 정적 평가**다. 깊이는 >0 이냐 아니냐(θ≥0.1)만 의미가 있다. `_get_adaptive_depth`(B:4954-4993)의 상향 조정도 결과에 영향 없음(후보 가지치기 폭만 바뀜, B:4995-5051). 진짜 탐색은 θ>1.0 롤아웃(B:4800-4952, 10수 × 후보 6)뿐이고 측정 격자(θ≤1.0)는 안 쓴다.
- **사람**: 1~2수 계획("이걸 집으면 아래 t5가 드러나고 독의 t5 두 장과 맞는다")은 흔하다 [추정]. 깊은 탐색은 안 한다.
- **판정: 부분.** "얕다"는 점은 사람과 비슷하지만, 사람이 하는 **"드러날 타일" 1수 계획을 봇은 전혀 안 한다**(C3).
- **방향**: 봇을 약하게 → 층이 깊은 레벨·후반 구간 음수 잔차와 같은 방향. 단 θ 적합이 평균을 흡수하므로 효과는 레벨 간 순위에서만 나온다.

### C3. 레이어 아래 가려진 타일 정보
- **게임 [UI]**: 덮인 일반 타일은 배경·아이콘 모두 50% 회색(`_deactiveColor` 0.5, Tile Base.prefab:77; Tile.cs:1469-1476). **위 타일과 겹치지 않은 부분의 아이콘은 보인다** → 타입이 보인다. 예외: unknown('?'), 닫힌 커튼, 스택 아래 장(가장자리만), craft 상자 속.
- **봇**: 후보·타입 수 = 집을 수 있는 타일만(`_get_accessible_type_counts` B:2191-2211, `ENABLE_HIDDEN_INFO_BLOCK=True` B:655). 덮인 타일 타입을 읽는 유일한 판단 경로 "STRATEGIC UNBLOCK BONUS"(B:3279-3334)는 `self._blocking_map` 미설정으로 **죽은 코드**(26 §1). → 봇은 사람이 **볼 수 있는** 정보(덮인 일반 타일 타입)를 안 쓴다. 롤아웃(θ>1)은 반대로 스택 속까지 다 본다.
- **판정: 불일치(봇이 정보 부족).** 사람보다 정보가 적은 쪽이다.
- **방향**: 봇이 약해짐. 층이 깊고 덮인 타일이 많은 레벨일수록 크다. 기믹 잔차와 직접 대응은 약하다(평균은 θ가 흡수).
- **제안(중)**: v2.5 항목 `dig_plan` — "이 수로 덮개가 사라지는 타일" 중 **독 타입과 같은 것**(덮인 일반 타일만, unknown·닫힌 커튼·스택 속 제외)에 가점. 죽은 코드를 살리지 말고 새 항목으로(v1~v2.4 동작 보존). 가중치 1개를 410레벨 θ0.85/1.0 그룹 내 ρ로 적합. 비용: 수당 노출 검사 1회(blocking map 이미 있음). 예상 효과: ρ 소폭(+0.01~0.03 [추정]), 평균은 θ 재적합 필요.

### C4. 무작위성·실수 모델
- **봇**: θ1.0 실수율 0.02, θ0.85 0.087(0.45−0.43θ, MC:27). 실수 = **θ0 시야 풀에서 균등 무작위**(B:4693-4698, 4792-4798). 성급 선택 확률 `clamp((0.5−patience)/0.3)` → θ≥0.5 이면 0(B:4740). 점수 잡음 `(1−pr)·U·2`(B:3662-3664) — 점수 단위(수십~수백)에 비해 작음. 기믹 위협은 v2.1 인지 확률(턴마다 독립 추첨, B:3993-4042)로 따로 표현.
- **사람**: 실수는 균등 무작위가 아니라 (a) 비슷한 아이콘 혼동, (b) 화면 위쪽·큰 덩어리 쪽 타일 선호, (c) 위협을 "한 판 내내" 못 보거나 계속 보는 **지속형** 주의 [추정]. 
- **판정: 부분.** 특히 기믹 인지가 **턴마다 독립**이라는 가정은 사람(한 번 숫자를 보면 계속 셈 / 처음부터 모르면 끝까지 모름)과 다를 가능성이 크다 [추정].
- **제안(중)**: 인지 추첨을 "판 시작 시 1회 + 턴 단위 갱신 확률"로 바꾼 변형(`aware_sticky`)을 bomb·grass·chain 에 시험. 적합 데이터: 기믹 실패 비중(AF 0.87/0.79/0.40)과 실패 시점(1-1 표). 풀·체인 포화(46%·10%) 해소 후보.

### C5. 첫 시도 — 맵을 처음 보는 사람 vs 봇
- AF 는 첫 시도 무도움 판만 쓴다[AF] → 사람도 맵을 처음 본다. 봇도 매 판 기억 없음 → **맵 경험은 같다**.
- 차이는 **기믹 경험**이다. 봇은 규칙을 완벽히 안다(인지 확률만 낮춤). 사람은 첫 등장 레벨에서 튜토리얼(냥이 강제 튜토리얼 AutoCollectController.cs:134-143, 기믹 해금 게이지 `GimmickUnlockGaugeUI.cs:36`)을 보고 레벨마다 배운다. v2.1 노출 학습 항(l0 0.5, τ 15)은 bomb·grass 만, 둘 다 가정값.
- 실패 팝업이 사유·기믹 아이콘을 보여 준다(UIFailReason.cs:180-210) → **다시 하기에서는 사람이 배운다**. 첫 시도 비교라 무관하지만, 재도전 클리어율(attempts_to_clear)을 쓸 때는 봇과 어긋난다.
- **판정: 일치(첫 시도 한정).**

3. **봇**: 스택 top = 일반 후보. 아는 것 = 남은 장 수(`remaining_inner`, B:3259)뿐 — 정보는 사람과 같다. 배출 임팩트 가점은 빈 칸 ≥2 + 목표가 있을 때만(B:3241-3272) → 대부분 레벨에서 꺼짐(17 §3). 17: 스택 top 고아율 0.069(일반 0.013의 5배), **독 5칸 이상에서도 스택 top 픽 비율 9.2% 그대로**. 18: θ1.0 고아 픽 77/77 이 "남은 수가 전부 짝 없는 스택 top" 인 **강제 상황** → 감점으로는 못 고침. θ: 실수 풀에서 스택 top 이 뽑힘(θ0.65 고아 108 중 96).
4. **판정**: **불일치 — 운용 순서.** 봇은 일반 타일을 먼저 소진해 막판에 스택만 남기고, 그때 독이 차 있다. 사람은 스택을 일찍(독 여유 있을 때) 연다 [추정].
5. **방향**: OLS −0.13(두 θ 유의). teleporter(−0.23 vs −0.02)·frog·ice·curtain·unknown·key·bomb 의 공존 몫도 같은 원인 → 고치면 봇 성공률↑ → **맞는 방향, 효과 범위 가장 넓음**.
6. **제안(상)**: v2.5 `stack_early` — 비매치 스택 top 픽에 `w·(빈 칸 − 3)` 가점(독 여유 있을 때 +, 독 ≥5 일 때 −), 남은 장 수가 많을수록 가중. 감점(18 1차)과 달리 **강제 상황 자체를 줄이는** 순서 정책이다. 적합: stack 188레벨 θ0.85/1.0, 손실 = 상대 MAE + 실패 시점(남은 0.60) 차. 가중치 격자 5점 × 64판 ≈ 188×5×2×64 판(판당 ~0.04 s → 워커 3개 ~1시간). 예상: stack 잔차 −0.10 → −0.05 [추정], 공존 기믹 동반 개선. 실패하면 Q4(사람 스택 운용) 실기 관찰이 필요.

### 3-12. craft
1. **규칙**: 상자에서 방향 칸으로 하나씩 배출, 상자가 덮이면 정지, 미배출 상자는 아래를 덮음(v2.3 `craft_cover`).
2. **사람**: 상자에 남은 개수 숫자 [UI](TileCraft.cs:197-199, 826-831), 다음 타입은 안 보임.
3. **봇**: 남은 개수만 앎(정합), 배출 임팩트 가점(목표 있을 때).
4. **판정**: 일치.
5. **방향**: OLS −0.01, 원값 +0.04. craft 레벨 봇 실패 사유 51% Bomb(사람 21%)은 공존 폭탄 몫.
6. **제안**: 없음(하).

### 3-13. key / 잠긴 독 칸
1. **규칙**: 잠긴 칸 = floor(key 타일 수/3), key 3장 매칭마다 1칸 해제(v2.3 `key_locks`).
2. **사람**: 자물쇠 칸이 보이므로 "지금 6칸"을 바로 안다 [UI]. key 를 우선 모은다 [추정]. 독 경고도 실제 빈 칸 기준(빈 칸 ≤2)으로 뜬다 [UI].
3. **봇**: key 픽 가점 8/15/25·ba + 잠김 기준 급함 가점(B:3344-3371) — 여기는 `unlocked_slots` 반영. 그러나 **일반 독 위험 감점(B:3081-3087)·선읽기 독 감점(B:6024-6029)은 7칸 기준 절대값(4/5/6)** → 1칸 잠기면 실패 칸(6)에서야 최대 감점. 사람 경고(빈 칸 2 = 4칸 점유)보다 한두 칸 늦다. 냥이 뱃지도 독 칸을 차지하지만 감점 기준은 그대로다.
4. **판정**: **불일치(봇 결함성).**
5. **방향**: 봇이 약해짐 → key 28레벨 잔차 −0.19(θ1.0)/−0.30(θ0.85)와 맞는 방향. 단 22/28 이 stack 공존이라 분리 필요.
6. **제안(상)**: v2.5 `dock_rel` — 감점 임계를 `unlocked_slots − 3/−2/−1` 로(7칸이면 현행과 동일 → 기본 레벨 무변화). 적합 파라미터 없음(규칙성 수정). 측정: key 28 + 냥이 41레벨 θ0.85/1.0 128판. 비용 작음. 예상: key 잔차 일부(+0.03~0.08 [추정]).

### 3-14. 냥이의 도움(autoCollect)
1. **규칙**: 사이클마다 뱃지 3장(덮임 무관, 같은 타입 ≤2)이 독으로, 뱃지가 모두 매칭되면 입력 잠그고 독의 미완성 타입을 필드에서 채움, 독이 비면 다음 사이클(26 §3).
2. **사람**: 자동(버튼·비용 없음), 첫 등장 강제 튜토리얼 [UI]. 뱃지에 발바닥 표시, 바구니 게이지 [UI](Tile.cs:1810-1830, AutoCollectController.cs:1330). 뱃지 타입을 먼저 맞추려 한다 [추정]. 냥이 레벨 클리어 169 s·실패 116 s(애니 포함) [AF], 실패 Normal 70%·Ice 12%·Chain 10% [AF].
3. **봇**: 뱃지 인식 없음(독 타입 짝 가점은 일반 로직으로 받음). v2.4 savvy(B:3904-3944, p_savvy 0.45)는 성공률 +0.01, 식별 불가. 독 감점 임계 절대값(3-13).
4. **판정**: 불일치, **원인 미확정**. 냥이 OFF v2.3 0.575 → ON 0.423 → AF 0.677(19 §4): 봇은 냥이가 **도움이 아니라 손해**인데 사람에겐 도움으로 보인다.
5. **방향**: −0.224, 봇이 약함.
6. **제안(상, 진단 먼저)**: ① 냥이 41레벨 계측 판(θ1.0 32판): 사이클 수, 뱃지가 독에 머무른 수, 실패 직전 독 구성(뱃지 vs 일반)을 기록. ② 결과에 따라 (a) `dock_rel` 적용(뱃지 칸 반영), (b) 뱃지 타입 우선 가점, (c) 냥이 수집이 스택·craft 속 타일까지 채우는지 게임 확인(19 §4 근사 "보드 위 타일만") — FindTilesInField(AutoCollectController.cs:1539-1555) 대상 범위가 봇과 다르면 규칙 차이. 비용: 계측 1회 짧게.

## 5. 기획자 확인 필요 질문 (추정 항목만, 예/아니오)
1. 독 경고(독 맥동)가 뜨면 플레이어가 **더 신중해진다**(실수가 줄어든다)고 보는가? (봇은 지금 독이 찰수록 실수를 늘린다)
2. 숙련 플레이어는 독 경고 전(4~5칸)부터 새 타입을 피하는가?
3. 플레이어는 커튼이 **다음 클릭에 열린다**(번갈아 바뀐다)는 것을 알고 기다리는가?
4. 플레이어는 스택을 **독이 비어 있을 때 일찍 열어** 타입을 확인하는 편인가?
5. 스택 아래 장의 **타입(아이콘)이 실제 화면에서 거의 안 보이는가**? (코드상 0.1칸 어긋남·어둡게 — 실기 확인 필요)
6. 플레이어는 **덮인 풀·체인 옆을 집어도 풀리지 않는다**는 규칙을 모르는 경우가 많은가?
7. 플레이어는 화면의 한 구역을 **몰아서(근처부터) 치우는** 습관이 있는가?
8. 폭탄 숫자를 한 번 본 플레이어는 **판 내내 계속 신경 쓴다**(턴마다 잊었다 떠올리지 않는다)고 보는가?
9. 폭탄 레벨에서 플레이어는 폭탄 타입 짝을 **미리 독에 모아 두고** 폭탄을 집는가?
10. 텔레포트 카운트(3단계)를 보고 **회전 직전에는 텔레포트 타일로 짝을 만들지 않는가**?
11. 초보는 링크가 **한 번에 2장** 들어간다는 것을 놓쳐 독 6칸에서 링크를 집다 지는 경우가 흔한가?
12. 플레이어는 key 타일을 **우선적으로 모으는가**?
13. 냥이 레벨에서 플레이어는 **발바닥 표시 뱃지 타입을 먼저 맞추려** 하는가?
14. 냥이 수집(2단계)은 **스택·craft 상자 속 타일도 끌어오는가**? (봇은 보드 위 타일만)
15. 실패가 아닌 일반 진행에서, 플레이어는 **덮인 타일의 어두운 아이콘을 보고 파낼 곳을 고르는가**?

질문 수 15. 1·5·14 는 화면/게임 코드 확인으로도 답할 수 있다.

## 6. 한계
- 사람 행동은 AF 집계(실패 사유·남은 타일·시간·연쇄)로만 본다. 수 단위 로그가 없어 "무엇을 집었나"는 전부 [추정]이다.
- OLS 는 레벨 단위 관측, 기믹 간 상호작용(stack×bomb 등) 미포함. CI 는 레벨 독립 가정. teleporter·frog 는 L391+ 에만 있어 구간 효과와 완전히 분리되지 않는다(17 §1).
- 실패 남은 타일 비교는 AF 레벨 중앙값 vs 봇 판 중앙값(정의 동일: 독 제외 보드 잔여, 16 §3-2).
- 게임 UI 는 코드·프리팹 읽기만 했다(실기·화면 미확인).
- 봇 줄 번호는 다른 세션 미커밋 변경이 있는 작업 사본 기준.
