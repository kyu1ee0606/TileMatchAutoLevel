# 솔버블 보장 재설계 — 역생성 + A* 검증 게이트

> 2026-06-16. 온라인 조사(마작 솔리테어 역생성, FreeCell A* 솔버, Room 8 난이도론) 근거.
> 현재 "forward 생성 → 휴리스틱 봇 검증"의 근본 한계(솔버블 미보장, 언클리어러블 오판,
> ÷3 버그)를 해결. 난이도 측정(스킬 스윕 θ/1-AUC/k)은 그대로 유지.

## 배경: 왜 바꾸나
- 휴리스틱 봇은 **솔버블을 증명 못 함** (해를 못 찾는 것 ≠ 해가 없음). optimal(lookahead10)도 가지치기 휴리스틱.
- 측정 결과 "언클리어러블"은 (a)수학적 불가능(÷3 위반) + (b)봇 한계 + (c)t0 분배 아티팩트의 혼합.
- 업계 정설: *"임의 레벨을 항상 푸는 알고리즘은 불가능, 그러나 풀리는 레벨 구성은 쉽다"* → **구성으로 보장**.

## 게임 메커니즘 (설계 전제)
- 타일은 레이어 스택. 좌표 `col_row`, 레이어 패리티(짝/홀)로 0.5칸 오프셋.
- **커버 규칙**: `_is_blocked_by_upper` — 같은 패리티는 동일 위치, 다른 패리티는 col 크기 비교로 4이웃 중 덮는 타일 존재 시 blocked. (기존 `_precompute_blocking_map` 재사용)
- 노출 타일(위에 덮은 타일 없음)만 선택 가능 → 독(7칸)으로 이동 → 같은 타입 3개 모이면 제거. 독 8개째 = 패배.

# 설계 1: 역생성 (Reverse / Constructive Generation)

## 핵심 아이디어
**"풀리는 witness 순서가 존재하도록 타입을 색칠한다."** 모양/레이어(=커버 의존성 DAG)는 기존 패턴/템플릿 그대로 두고, **타입 배정**만 독≤7을 지키는 peeling 순서가 존재하도록 구성. 그 순서가 곧 해의 증거 → 솔버블 100% 보장.

## 알고리즘

### 입력
- 배치된 위치 집합과 레이어(기존 생성기 산출) → 커버 의존성 DAG (`pos A는 pos B가 제거돼야 노출`).
- 목표 타입 수(useTileCount), 기믹 배치(별도 단계).

### 단계
1. **DAG 구성**: 각 타일 위치에 대해 `_precompute_blocking_map`으로 "이 타일을 덮는 상위 타일들"을 구함 → 위상 의존성.
2. **Witness peeling 시뮬레이션** (타입 미정 상태로):
   - 가상 독(빈 슬롯 7), `open_groups`(미완성 그룹들) 추적.
   - 매 스텝: 현재 노출된(in-degree 0) 위치 중 하나를 골라 "제거" 후보로 꺼냄.
   - 이 위치에 **타입을 배정**: 가능하면 진행 중인 open_group에 합류(2개→3개 완성해 독 비움), 아니면 새 그룹 시작.
   - **제약**: `len(open_groups) ≤ 7` 항상 유지. 새 그룹을 못 열면(독 꽉참) 기존 open_group을 완성시킬 수 있는 노출 위치를 우선 선택.
3. **타입 마감**: 모든 위치를 3개씩 그룹으로 묶고(총 위치 ÷3 보장), 각 그룹에 타입 부여. 그룹 멤버의 peel 인덱스 간격 = 난이도 레버.
4. **검증(자가)**: 구성한 witness 순서를 그대로 forward 재생 → 독 오버플로 없이 전부 제거되는지 assert (구성이 맞으면 항상 통과).

### 난이도 제어 (스킬 스윕과 연결)
- **그룹 멤버 peel 간격을 좁게** → 매치가 곧바로 보임(쉬움, θ0 낮음).
- **간격을 넓게(독≤7 한도 내)** → 타일을 오래 들고 계획해야 함(어려움, θ0 높음). 단 witness 순서가 여전히 독≤7이라 **반드시 솔버블**.
- 즉 난이도 = "witness 외의 그리디 경로로도 쉽게 풀리는가"를 스킬 스윕이 측정. 역생성은 하한(반드시 풀림)을 보장, 스킬 스윕은 체감 난이도를 측정 — 역할 분담.

### 기믹 처리
- chain/ice/grass 등은 **witness 순서에 추가 제약**으로 인코딩:
  - chain: 좌우 클리어 가능 이웃이 witness 순서상 먼저 와야 함.
  - key/lock: key 그룹이 lock보다 witness상 먼저 제거.
  - 복잡 기믹(teleport/frog)은 v1에서 witness 시뮬에 단순 모델 적용, 불확실하면 해당 그룹은 기믹 미부여.

### 장점/한계
- ✅ 솔버블 100% 보장, ÷3 위반 원천 차단, 언클리어러블 false positive 소멸.
- ✅ O(n) 구성 — 시뮬 검증 불필요(생성 단계에서 끝).
- ⚠️ 시각적 패턴/템플릿과 타입 배정의 결합 — 기존 패턴 색상 의도와 충돌 가능(타입이 witness 제약을 따라야 함). 모양은 유지되나 "어느 칸이 무슨 색"은 역생성이 결정.
- ⚠️ 기믹 조합이 많을수록 witness 제약 인코딩 복잡 — 단계적 적용.

### 구현 위치
- `backend/app/core/reverse_generator.py` (신규): DAG + witness peeling + 타입 배정.
- 기존 `generator.py`의 배치 단계 후 타입 배정을 역생성으로 교체(플래그 `use_reverse_generation`).
- 기존 `_ensure_no_deadlock` 봇 시뮬 검증 **제거 가능**(구성 보장이므로) → 생성 속도 추가 향상.

# 설계 2: A* 솔버 검증 게이트

## 목적
손편집/템플릿/기존 저장 레벨처럼 **구성 보장이 없는** 레벨을 **양방향 확정 판정**:
해 발견 → PROVEN_SOLVABLE(witness 반환), 상태공간 소진 → PROVEN_IMPOSSIBLE, 예산 초과 → UNCERTAIN.

## 상태 정의
```
State = (frozenset(remaining_positions), tuple(sorted(dock_types)), gimmick_state_hash)
```
- remaining_positions: 아직 안 뽑힌 (layer, col_row) 집합.
- dock: 미완성 타입 멀티셋 (완성 3개는 즉시 제거되므로 각 타입 0~2개, 합 ≤7).
- gimmick_state: ice 잔여, chain 잠금, frog 위치 등 (있을 때만).

## 탐색
- **A\***: f = g + h. g = 사용한 이동 수, h = 남은 타일 수 / 3 (제거에 필요한 최소 매치 수 = admissible 하한).
- **이동 생성**: 현재 노출된 타일 각각을 독에 추가 → 3매치 시 자동 제거.
- **메모이제이션**: 방문한 (remaining, dock) 해시 저장 → 순서만 다른 동일 상태 재방문 차단 (상태공간 폭발의 핵심 완화).
- **Forced-move 가지치기**: 독에 같은 타입 2개 + 노출 타일에 그 타입 존재 → 즉시 매치(분기 안 함, dominance).
- **노드 예산**: 기본 200k~500k 상태(fc-solve 수준). 초과 시 UNCERTAIN.

## 판정
- goal(remaining 비고 dock 비음) 도달 → **PROVEN_SOLVABLE** + witness 이동열.
- 프런티어 소진(미방문 상태 0) → **PROVEN_IMPOSSIBLE**.
- 예산 초과 → **UNCERTAIN** (휴리스틱 봇 결과로 폴백 표시).

## 기믹 모델링 (난이도 = 구현 비용)
- v1: 기믹 없음 / ice·grass(단순 카운트다운)·key·lock·chain까지. 이동 합법성/상태 전이만 추가.
- v2: bomb(턴 카운트), curtain(은닉), teleport(셔플), frog(이동) — 상태공간/비결정성 큼. 미지원 기믹 포함 레벨은 UNCERTAIN 처리.

## 상태폭발 완화 (FreeCell 솔버 근거)
- 메모이제이션 + forced-move + admissible h + 노드 예산 캡.
- 독≤7 + 노출 타일만 분기 → 분기계수 제한적(보통 10~30). 메모이제이션이 수렴시킴.
- 그래도 큰 레벨(200+ 타일)은 UNCERTAIN 가능 — 그땐 역생성 레벨이면 애초에 불필요(보장됨).

## 병렬화 (RL 하니스 재사용)
- 레벨 단위로 `_get_gen_pool()` 프로세스 풀에 분배 (배치 검증과 동일 패턴).
- 단일 레벨 내부는 단일 A* (탐색은 순차) — 여러 레벨을 코어별 병렬.

## 구현 위치
- `backend/app/core/solver.py` (신규): 상태/이동/A*/메모이제이션.
- `backend/app/api/routes/analyze.py`: `/api/analyze/solvability` 엔드포인트 (단일/배치).
- 프론트: RL 탭 "언클리어러블 의심" 레벨에 "정적 솔버 판정" 버튼 → PROVEN_IMPOSSIBLE/SOLVABLE/UNCERTAIN 배지.

# 통합 파이프라인 (목표 상태)

```
생성:   역생성(설계1) → 솔버블 보장 + ÷3 보장   [봇 데드락 검증 제거]
난이도: 스킬 스윕(기존) → θ0/1-AUC/k 측정·자동교체
검증:   구성 보장 안 되는 레벨만 A*(설계2) → 양방향 확정
        (기존 저장 레벨 일괄 재판정 → 언클리어러블 분류 정정)
```

## 권장 구현 순서
1. **A\* 솔버(설계2) 먼저** — 위험 낮고(생성 안 건드림), 즉시 가치:
   기존 "언클리어러블" 레벨들을 PROVEN_IMPOSSIBLE / SOLVABLE / UNCERTAIN로 정정 분류,
   ÷3 버그 레벨 확정. 현 RL 탭에 바로 붙음.
2. **역생성(설계1) 다음** — 토대 교체(큰 변경)라 A*로 "역생성 결과가 정말 솔버블"을 교차검증하며 안전하게 도입.
   먼저 무기믹/단순기믹부터, 점진 확대.

## 리스크
- 역생성: 시각 패턴과 타입 배정 결합, 기믹 조합 인코딩 복잡도 → 단계적.
- A*: 복잡 기믹 상태폭발 → 예산 캡 + UNCERTAIN 폴백으로 안전.
- 둘 다 기존 파이프라인과 **병행**(플래그/별도 엔드포인트) — 한 번에 교체하지 않음.
