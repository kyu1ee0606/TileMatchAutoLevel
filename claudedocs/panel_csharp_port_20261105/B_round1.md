## 핵심 논거

### 1. 성능 성과는 충분히 크지만, 전체 이식의 경제성까지 증명하지는 않는다

- [사실·문서] v6는 그리디 CPU 26.7배, θ1.3 CPU 58.7배이며 유휴 단독 측정은 아니다. R2 2,340칸·140,400판의 rate·첫 클리어 시드·경로 일치가 기록돼 있다. 이 성과를 무시하고 처음부터 Python 최적화만 택할 근거는 약하다. (계획 §8, 261~267행; 조사 §1-1, 27~28행)
- [사실·지시] AI 세션 중심 개발에서 ①의 13~18인일 예상은 하루 남짓의 1차 완료로 단축됐다. [추정] 따라서 37~52인일을 사람 인건비로 곱해 반대하는 것은 부적절하다. 다만 1차 구현 속도를 장기 운영·기믹 변경·실사용 shadow 기간까지 동일 비율로 축소할 근거도 없다. 비용은 AI 실행 비용, 사람의 검토·판정 시간, 회귀 계산량, 장애 대응, 반복 변경 비용으로 다시 기록해야 한다. (마더 지시의 AI 개발 참고; 계획 §5, 217~223행)
- [사실] 현 봇 연결의 `on`은 shadow로 해석된다. autoplay는 Python 계산을 끝낸 뒤 C# 재실행을 제출한다. [추정] 코어 완료와 맵툴 사용자 지연 개선은 별개이며, 추가 투자 판단에는 요청 전체 지연·사용 빈도·폴백 비율이 필요하다. (backend/app/core/tilecore_bot.py:52; backend/app/api/routes/analyze.py:567,637,643; 계획 §7, 242행)

### 2. 장기 비용의 중심은 두 언어보다 두 정본이다

- [사실] Python BotSimulator는 현재 7,040줄이며 초기화·합법 수·상태 복사·수 적용·점수 함수가 한 파일에 있다. C#은 `bs`에서 Python 버그까지 보존하고, 장기적으로 `game` 등 별도 의미론을 계획한다. (직접 `wc -l`; backend/app/core/bot_simulator.py:1150,2270,2463,2673,3186; 계획 §2-1·§3-1)
- [추정] 신규 기믹 하나는 최소 **Python 도구 규칙 + C# bs 규칙의 두 구현**에 반영해야 한다. 게임까지 포함하면 게임 원본을 더한 **세 구현 경계**이고, 초기화·상태 복사·이동·점수·회귀 자료가 추가 수정 후보다. 이는 정확히 세 파일이라는 뜻이 아니다. 프로토콜에 새 상태·결과가 생기면 어댑터도 바뀐다. (근거: 위 함수 분리, 계획 §2 B/C·§3-1·§4-1)
- [사실] Python 제거는 안정화 후 별도 결정이며, 미지원 프로필·통계 필드·상태 단위 solver/TrackingBot 사용이 남아 있다. [추정] 현재는 Python 코어 전체 제거가 불가능하다. 제거하려면 호출처·정책·출력·상태 API의 사용 목록을 닫고, C#을 규칙 정본으로 정한 뒤 Python 실행 경로를 폐기해야 한다. 그 후 Python 오라클을 동결 보관할 수 있으나 새 기믹 검증은 별도 골든 자료/게임 오라클이 맡아야 한다. (계획 §0-A 6; 조사 §1-2·§2-1·§2-8·§2-9)

### 3. 상주 워커는 타당하나, 버전·장애 경계부터 완성해야 한다

- [사실·문서] 조사 당시 `~/tilecore`는 git 저장소가 아니었다. 계획은 별도 저장소·불변 버전·시작 시 버전 확인을 요구한다. [사실·직접] 현재 git status에서 `tilecore_bot.py`·`tilecore_shadow.py`는 `??`, `analyze.py`·`solver.py`는 `M`이다. DLL 경로는 v6로 고정되지만 현재 봇 호출부는 존재 확인 후 바로 실행한다. **경로 고정과 소스·빌드 재현성은 다른 보장**이다. (조사 §1-1,17행; 계획 §3-2; backend/app/core/tilecore_bot.py:44,116~148)
- [추정] 후속 작업의 첫 완료 기준은 소스 버전과 바이너리 해시·규칙 버전·프로토콜 버전의 대응, 지원 기능 협상, 제한된 큐와 요청 ID, 타임아웃·취소·EOF·재시작 시 대기 요청 처리, Python 폴백 계측이어야 한다. 기존 Python 풀마다 C#을 띄우면 계획의 워커 하나라는 장점이 사라질 수 있어 프로세스 소유권도 정해야 한다. (계획 §3-2·§3-3·§6; backend/app/api/routes/analyze.py:556,616,636)
- [추정] 폴백은 정확성뿐 아니라 용량 설계 대상이다. C# 처리량을 전제로 요청량을 늘렸다가 느린 Python으로 모두 되돌리면 지연이 급증할 수 있다. 따라서 장애 시 폴백 동시 수·대기 한도를 검증해야 한다. 현 shadow 오류 무시는 C# 결과를 서비스하는 `on`의 장애 검증을 대신하지 못한다. (계획 §0-A 5; backend/app/core/tilecore_bot.py:12~18,133~148)

### 4. shadow는 유지하되 비교 가능성과 통계 기준을 먼저 고쳐야 한다

- [사실] `seed=None`은 현재 `skip_seed_none`으로 빠지고, 실시간 비교는 판별 cleared 비트열을 비교한다. 반면 autoplay 응답은 평균·최소·최대 이동 수, combo, 분산도 사용한다. **현재 실시간 불일치 0만으로 응답 전체의 동일성을 주장할 수 없다.** (backend/app/core/tilecore_bot.py:185~198,208~214; backend/app/api/routes/analyze.py:581~592)
- [사실] 새 BotSimulator의 RNG는 `random.Random()`이고 시드 인자는 선택적이다. 생성·batch-verify의 시드 없는 경로와 t0 시간 시드는 별도 문제다. (backend/app/core/bot_simulator.py:874~888; 조사 §1-2,34행·§2-2·§2-6)
- [추정] 회귀용으로 입력·시드 목록·프로필·엔진 버전을 고정해 결정적 동등성을 검사하고, 실제 무시드 경로는 별도 분포 검증으로 유지하는 편이 디버깅 비용이 작다. 양쪽에 같은 명시 시드를 주는 새 실행 계약은 유용하지만 기존 `seed=None`의 RNG 흐름과 의미가 같다고 단정해서는 안 된다. 도입 전 RNG 소비·조기 종료·t0 동작을 검토해야 한다. (계획 §0-A 3; 조사 §3,114~117행)
- [추정·산술] 독립 이항 표본에서 양쪽 성공률이 약 50%, 각 300판이면 차이의 정규근사 95% 구간 반폭은 `1.96*sqrt(0.25/300+0.25/300) ≈ 8.0%p`다. 1,000판도 약 4.4%p로, ±3%p 동등성에 충분한 보편 기준이 아니다. 다중 비교 보정은 더 엄격해진다. 조기 종료 표본에는 고정 표본 공식을 그대로 적용해서도 안 된다. 표본 수와 중단 규칙을 확정하고, 유의차 없음과 동등성 입증을 구분해야 한다. (검토 대상: 계획 §0-A 3,45행; 조기 종료: backend/app/core/bot_simulator.py:877~889)
- [추정] shadow 기간만 채우기보다 기믹·프로필·입력 크기별 비교 성공률, skip/unsupported/queue drop 비율, 응답 필드 비교를 게이트에 넣는다. 코어의 고정 회귀는 재사용하되 새 호출처의 시드·집계·조기 종료 계약은 별도 확인한다. 이 방식은 게이트를 없애지 않고 반복 검증 비용을 줄인다. (계획 §0-A·§4-2; backend/app/core/tilecore_bot.py:15~26; 조사 §3)

### 5. 다음 투자 단위는 좁게 잡을 수 있고, 여기서 멈춰도 자산은 남는다

- [사실·문서] 생성 시간의 97~99%가 봇 검사였고 생성 본체는 ≤0.3초였다. gen_optimal은 이미 검증된 범위지만 `serve`와 어댑터가 남아 있다. 검증 루프의 fast_mode, MC의 기본 v1 계열, 출력 통계에는 확인할 공백이 있다. (계획 §1-2·§2-2; 조사 §2-2·§2-3·§2-8)
- [추정] 따라서 **배포·계약 정리 → serve/어댑터 → 막힘 검사 → 실사용량 기반 선택**으로 수정한다. 그 뒤 검증 루프·batch-verify의 봇 부분과 v24 MC 중 실제 절감량이 큰 것을 택한다. MC/RL/tune 전 버전 이식이나 A*까지 자동으로 약속하지 않는다. A*는 단순 연결이 아닌 bs 상태용 탐색이며, 판정 확정률의 추가 가치로 별도 평가한다. (조사 §2-1·§2-6·§2-8; 현재 FastJudge의 다른 규칙: backend/app/core/tilecore_shadow.py:7~10)
- [추정] 지금 멈추면 검증된 봇 CLI와 회귀 자료는 배치 가속 자산으로 남지만, 맵툴은 현재 Python 결과를 계속 쓰므로 서비스 가속은 남지 않는다. C#을 활성 유지하면 두 구현 동기화 비용이 남고, 동결하면 새 기믹·정책 지원을 포기해야 한다. **중단은 부채 삭제가 아니다.** 중단 시에도 지원 버전·범위·재현 가능한 산출물을 정리하고 shadow 전용이라는 상태를 명확히 남겨야 한다. (조사 §1-1·§1-3; 계획 §8; backend/app/core/tilecore_bot.py:13,44,52~57)

## 가장 큰 위험

1. **비교하지 못한 요청이 많은데 '불일치 0'을 전체 보증으로 해석하는 것.** seed skip·프로필 공백·통계 출력 누락을 별도 분모로 공개해야 한다. [추정: 논거 4, 조사 §1-2·§3]
2. **소스·바이너리·규칙의 출처를 고정하지 않은 상태에서 두 정본과 폴백을 운영하는 것.** 재현·롤백·기믹 수정 누락 비용이 빠른 초기 구현 이득을 잠식할 수 있다. [추정: 논거 2~3, 계획 §3-2]
3. **하나의 코어 성능 성공을 미검증 호출처 전체의 경제성으로 확대하는 것.** 미사용 정책·A*까지 넓히면 AI 구현 시간보다 검토·회귀·운영 시간이 지배할 수 있다. [추정: 논거 1·5, 조사 §5]

## 성능 패널에게 던질 질문

1. 생성기 막힘 검사까지 연결했을 때와 그 뒤 MC 전 버전·A*까지 확장했을 때, **실제 주간 호출 수 × 요청 전체 절감 시간 × 지원 비율**은 각각 얼마인가? 현재 26.7/58.7배로 입증된 범위와 추가 측정이 필요한 범위를 나눠 어떤 다음 한 단계를 선택하겠는가? (근거: 계획 §8 속도; 조사 §2·§5)
