# 13. AF 실제 유저 클리어율 — 봇 보정용 데이터 점검 (1단계)

- 작성: 2026-10-14 · 분석 전용(코드·서버·게임 저장소 무수정)
- 질문: AppsFlyer 로우 데이터로 레벨별 실제 유저 클리어율을 만들 수 있는가? 그 값으로 봇을 보정(2단계)할 수 있는가?
- 재현: `backend/.venv/bin/python backend/scripts/af_level_metrics.py` (약 3분)
- 데이터: `backend/data/pv_sandbox/af_calibration/level_metrics.json`, `level_metrics.csv`. 레벨 1~1500, 집계값만 들어 있고 식별자는 없다.

## 0. 결론 먼저

1. **2단계 보정은 가능하다. 단, 대상은 L32~500 이고 맞출 값은 "점 하나"가 아니라 "범위 + 순위"여야 한다.**
   - 표본은 충분하다. 첫 시도·무부스터·무부활 판이 30판 이상인 레벨이 911개, 100판 이상이 507개다. L32~500 은 거의 모든 레벨이 100판 이상이다.
   - 가장 큰 오차는 표본이 아니라 **부스터 선택 편향**이다. 무부스터 판만 골라 낸 클리어율(L32~100 96.1%)은 유저가 도움 없이 깼을 비율을 **과대 추정**한다. 도움 없이 깼을 실제 비율은 하한~상한 사이에 있다. 구간 단위로 L32~100 은 77.5~89.9%, L101~300 은 76.3~85.8% 이다(§3, §5-1).
   - 레벨 난이도 **순위**는 어느 지표로 재도 거의 같다. 판 ≥100 레벨에서 Spearman 0.90~0.97 이다. 그래서 보정 1순위 목표는 **봇의 레벨 순위가 유저 순위와 맞는 것**, 2순위는 **구간별 무도움 클리어율이 하한~상한 범위 안에 드는 것**으로 둔다.
2. **맵 일치**: 레벨 델타 갱신은 v1.10.1025 이후 꺼져 있다. 그래서 유저는 **앱 빌드에 들어 있는 샤드 맵**으로 플레이했다. 버전마다 빌드 샤드를 에디터 LIVE 3차와 비교한 결과는 다음과 같다(§6).
   - L32~1500: 1,466개 일치. **불일치 34개**(32~34·36~44·46~49·61~64·66~71·73~79·341, 2차 배치 맵, 그중 Lv34 는 구조도 다름).
   - L1~31: 1.1.0·iOS 2.1.0 은 31개 전부 일치한다. 1.0.162 는 20개가 다르므로 이 20개는 **버전 혼재**로 분류했다.
3. **쓰기 어려운 구간**: L501~1000 은 레벨당 첫시도 무도움 판의 중앙값이 48판이고, 상위 10명이 21%를 차지한다. **레벨 단위로는 쓰지 말고 100레벨 묶음으로만** 쓴다. L1001~1500 은 유저가 36명뿐이라(상위 10명이 51%) **보정 근거에서 제외**하고 참고로만 본다.

## 2. 방법

### 2-1. 판 재구성 (게임 위키 IMPL_SPEC §V2-2-3·§V2-6 규칙 + 보정 1개)
- 기기별로 시간순 정렬한다. 같은 초는 clear → fail → revive → retry → start → booster 순서로 놓는다. `level_start` 가 판을 연다.
- 결과 분류:
  - 클리어
  - 최종 실패: 마지막 fail 뒤에 revive 가 없음
  - 기록 없음: 포기·강제 종료·불명. 둘은 구분할 수 없다
  - 관측 끝 미종료(censored)
- **보정(이번 추가)**: 오프라인으로 쌓였다가 한꺼번에 전송된 이벤트는 start 와 clear 가 같은 초에 찍힌다. 이 경우 정렬 규칙(clear 를 start 앞에 둠) 때문에 이번 판의 clear 가 **직전 판에 붙는다**. 기존 규칙으로는 종료 이벤트 level ≠ 판 level 인 경우가 17,980건(3.3%)이었다.
  - 보정 방법: 종료·부활·부스터 이벤트를 **같은 `level` 의 열린 판**에 붙인다. 같은 초에 그 레벨의 start 가 있으면 이벤트를 start 뒤로 미룬다.
  - 결과: 14,145건을 미뤘고 3,471건을 직전 판이 아닌 판에 붙였다. 기록 없음은 23,592 → 15,398 로 줄었다.
  - 클리어율 영향은 구간별로 +0.1~0.7%p 로 작다(기존 규칙 결과는 `--legacy-order` 로 재현).
- 붙일 판이 없는 이벤트도 남았다: clear 4,530(0.9%) · fail 658 · revive 477(대부분 무한 모드 부활) · booster 1,399. 원인은 start 유실과 무한 모드다.

### 2-2. 정의
| 용어 | 정의 |
|---|---|
| 첫 시도 | 그 기기가 그 레벨을 처음 관측된 판이면서 `attempt=1`. 첫 관측 판의 attempt 분포는 1: 497,288 · 2: 902 · 3+: 281 이다 |
| 도움 | 그 판에서 `item_used>0`, `booster_use_*` 1건 이상, `level_revive` 1건 이상 중 하나라도 있음 |
| **clean_ft 클리어율** | 첫 시도·무도움 판 중 클리어 비율. 분모는 클리어+최종 실패이고 Wilson 95% CI 를 붙였다 |
| 무도움 하한 (LB) | 무도움 첫시도 클리어 ÷ 첫시도 종료 판 전체. 도움 받은 판은 전부 "도움 없었으면 실패"로 본다 |
| 무도움 상한 (UB) | (무도움 클리어 + 실패 이벤트 없이 부스터만 쓰고 클리어한 판) ÷ 첫시도 종료 판 전체. 부활(=이미 실패)이 있거나 부스터를 쓰고도 실패한 판은 무도움이면 실패로 본다 |
| 클리어까지 시도 | 첫 관측 판이 첫 시도인 (기기, 레벨) 쌍에서 첫 클리어까지의 판 수. 기록 없는 판도 포함한다 |
| tiles_left · combo_max · play_sec | 첫시도 무도움 판의 값. 계측은 1.0.162.10 이후다 |

## 5. 편향 점검

### 5-1. 부스터 선택 편향 — 가장 큼
- clean_ft 클리어율이 무도움 **상한보다 높다**. 32–100 구간이 96.1% 대 89.9% 이다.
- 이는 "부스터 사용이 판 결과와 무관하다"는 가정과 맞지 않는다. 실제로 도움 받은 판의 약 36%(32–100 기준)는 실패 이벤트가 있었던 판이다(부활 사용, 또는 부스터를 쓰고도 최종 실패). 유저는 **어려운 판에서 부스터를 쓴다**. 그래서 무부스터 판만 골라 내면 쉬운 판만 남는다.
- 결론: 봇(부스터 없이 플레이)과 비교할 값은 clean_ft 하나가 아니라 **[하한, 상한] 범위**다. 범위 폭은 구간 기준 7~13%p, 레벨 기준으로는 더 넓다.
- 다만 레벨 순위는 지표와 무관하게 안정적이다. Spearman(clean_ft, LB) 은 n≥30 에서 0.85, n≥100 에서 0.90 이고, (LB, 도움 사용률) 은 0.96~0.97 이다.

### 5-2. 생존 편향
- 비교 방법: 같은 기준(L32~100 첫시도 무도움 클리어율, 그 구간에서 10판 이상 플레이한 기기)으로 뒤 구간까지 도달한 유저와 전체 유저를 비교했다.

  | 대상 | 기준 클리어율 평균 | 도움 사용률 평균 |
  |---|---:|---:|
  | 전체 (1,932대) | 0.960 | 0.20 |
  | 101–300 도달 (981대) | 0.96 | 0.18 |
  | 301–500 도달 (222대) | 0.97 | 0.16 |
  | 501–1000 도달 (73대) | 0.97 | 0.17 |
  | 1001–1500 도달 (12대) | 0.97 | 0.15 |

- 실력 차이는 작다(+1%p). 하지만 뒤 구간일수록 **도움을 덜 쓰는 유저**가 남는다. 뒤 구간 유저층은 1~5%p 쯤 더 잘하고 부스터를 덜 쓰는 집단이다.
- 따라서 같은 봇이 앞 구간에 맞으면 뒤 구간에서는 사람보다 약간 약하게 보인다. 이 차이를 레벨 난이도로 읽으면 안 된다.

### 5-3. 버전 혼재
- L32 이상(맵 동일) 구간에서 1.0.162 와 1.1.0 의 clean_ft 차이:

  | 구간 | 1.0.162 | 1.1.0 | 차이 |
  |---|---:|---:|---:|
  | 32–100 | 96.2% | 96.0% | −0.2%p |
  | 101–300 | 93.7% | 92.7% | −1.0%p |
  | 301–500 | 91.8% | 90.7% | −1.1%p |
  | 501–1000 | 92.0% | 92.8% | +0.8%p |

  차이는 ±1.1%p 안이다.
- 도움 사용률은 1.1.0 이 2~4%p 높다(32–100: 18.5 → 22.1%). 경제나 UI 변화로 보이지만 확인하지 않았다.
- L1–31 은 버전마다 맵이 다르다(§6). 1.0.162 96.8% 대 1.1.0 98.5% → 1.1.0·iOS 부분집합만 써야 한다.
- 1001–1500 구간(1.0.162 92.7% 대 1.1.0 80.9%)은 유저 수가 적어 버전 효과가 아니라 사람 차이다.

## 6. 맵 일치 — 실제 플레이된 맵 = 앱 빌드 내장 샤드

- 근거:
  - `LevelDeltaUpdater.SyncInBackground` 호출이 v1.10.1025(08-24경)부터 주석 처리돼 있다(`LevelController.cs:382`, `LevelDeltaUpdater.cs:35`).
  - `LoadLevel` 은 L1 델타 → L2 baked 순서로 읽는다. 서버 단건 조회도 `GBRealArray.No`(로컬)로 고정돼 있다(`LevelMapProvider.cs:311-315`).
  - 따라서 **판의 맵은 그 앱 버전 빌드에 들어간 `StreamingAssets/GBoost` 샤드**다. 서버(GameBoost)의 이후 변경은 반영되지 않는다.
- 버전 → 샤드 커밋 대응: 버전을 반영한 커밋 직전의 마지막 샤드 변경 커밋으로 잡았다. 게임 저장소는 `git show` 로 읽기만 했다.
  - 1.0.162 → `a2229a5d` (09-08). 버전 재부여 커밋 `b4ce386f`(09-08) 직전이다.
  - 1.1.0 / iOS 2.1.0 → `b741f6a3` (09-21). 플랫폼 버전 반영 커밋 `727328a9`(09-29) 직전이다.
  - 샤드 커밋 사이 변경은 09-16 과 09-21 두 번뿐이다. 빌드가 커밋 상태와 정확히 같은지는 빌드 기록으로 확인하지 못했다 → 신뢰도는 "높음(추정)".
- 비교 기준: 에디터 LIVE 3차(`pv_20261002_live3/source.json`, batch_1789636723287)와 `canonical_map` 기준 전체 해시(타입 포함)·구조 해시(타입 제외).

| 샤드 | 에디터와 같음 | 타입만 다름 | 구조 다름 |
|---|---:|---:|---:|
| b741f6a3 (1.1.0·2.1.0) | 1,466 | 33 | 1 (L34) |
| a2229a5d (1.0.162) | 1,446 | 34 | 20 (L4–17·20·25·27·30·31·34) |

| 분류 (판의 버전 구성 기준) | 레벨 수 | 레벨 |
|---|---:|---|
| **same** — 모든 판이 에디터와 같은 맵 | 1,446 | L1~31 중 11개 + L32~1500 의 나머지 |
| **mixed** — 1.0.162 판만 다름 | 20 | L1·4–17·20·25·27·30·31 → 1.1.0·iOS 판만 쓰면 same |
| **mismatch** — 모든 버전에서 다른 맵(2차 배치) | 34 | 32–34·36–44·46–49·61–64·66–71·73–79·341 (L34 는 구조도 다름) |

- mismatch 34개는 2단계에서 두 가지 중 하나로 처리한다: (a) 제외하거나, (b) 봇에게 **샤드 맵(2차 배치)**을 그대로 플레이시킨다. 표본이 많은 L32~79 가 대부분이므로 (b)를 권장한다.
- **불확실한 점**:
  - ① 빌드가 커밋과 다른 로컬 상태에서 만들어졌을 가능성.
  - ② L1~31 일부와 count-only 컨테이너 70개(02 노트)는 클라가 플레이할 때마다 내부 타입을 랜덤으로 정한다. 맵 해시가 같아도 판마다 실제 배치가 다를 수 있다.
  - ③ 앱 업데이트를 안 한 유저는 없다고 보았다. 이번 분석은 판마다 버전별로 판정하므로 영향이 없다.

## 7. 2단계(보정) 제안

**사용 범위**
- L32~500: 개별 레벨 단위로 쓴다. 대상은 same 맵이면서 판 ≥100 인 레벨이다. 32–100 은 36개, 101–300 은 200개, 301–500 은 184개다.
  - mismatch 33개를 샤드 맵으로 돌리면 32–100 은 69개가 된다.
  - 부스터 튜토리얼 L35·45 는 제외한다.
- L1~31: 1.1.0·iOS 판만 쓴다. 튜토리얼 성격이 강하므로 보조로만 쓴다.
- L501~1000: 100레벨 묶음 단위로만 쓴다. 판 ≥30 레벨(410개)은 순위 검증에만 쓴다.
- L1001~1500: 보정에 쓰지 않는다(유저 36명).

**맞출 지표 (우선순위)**
1. **레벨 난이도 순위**: 봇 클리어율과 유저 지표의 Spearman 상관. 유저 쪽 기준은 LB 와 clean_ft 둘 다 쓴다. 목표는 ≥0.7 로 둔다. 근거: 유저 지표끼리의 상관이 0.85~0.97 이다.
2. **구간별 무도움 클리어율 범위**: 봇 클리어율이 구간의 [LB, UB] 안에 들어야 한다. 예: 32–100 은 77.5~89.9%, 101–300 은 76.3~85.8%, 301–500 은 71.8~81.2%. 레벨 단위로는 [LB, UB] 를 벗어난 레벨의 비율로 평가한다.
3. **실패 형태**: fail_reason 구성(Normal / Grass / Bomb / Chain / Ice)과 실패 시 tiles_left 분포(p25/p50/p75). 클리어 판의 combo_max 분포는 보조로 본다.
4. (선택) 도움 사용률. 하한과 강하게 연동되므로(ρ≈0.97) 난이도의 대리 신호로 쓸 수 있다.

**예상 오차 한계** (봇과 유저를 비교할 때 이보다 작은 차이는 구분할 수 없다)
| 원천 | 크기 |
|---|---|
| 부스터 선택 편향 (정의상 불확실) | 구간 7~13%p, 레벨은 더 큼 → 절대값 비교의 기본 오차 |
| 표본 (레벨 n≥100) | ±2.5~5%p (유저 군집 고려 시 더 큼) |
| 기록 없음 처리 | 2~4%p |
| 생존 편향 (구간 간 비교) | 1~5%p |
| 버전 혼재 (L32+) | ±1%p |
| 판 재구성 규칙 | ≤0.7%p |

→ **레벨 하나의 절대 클리어율을 ±5%p 안으로 맞추는 것은 이 데이터로 검증할 수 없다.** 구간 범위와 순위로 맞추는 것이 현실적인 목표다.

**데이터 보완책**
1. **계측 추가 — 가장 효과가 큼**
   - 부스터를 쓴 시점에 "그 판에서 이미 실패했는지"와 "쓰기 직전 보드 잔여"를 남기면, 부스터 선택 편향 범위를 좁힐 수 있다. 방법은 `booster_use_*` 에 `tiles_left`·`fails_so_far` 를 추가하는 것이다.
   - 포기를 따로 남기는 `level_quit` 이벤트(IMPL_SPEC K1).
   - 판 맵 식별값(샤드 etime 또는 맵 해시) — 맵 일치를 추정이 아니라 사실로 확인할 수 있다.
2. **기간 확대**: L501+ 는 유저 수가 병목이다. 4주를 더 모아도 유저 증가는 제한적이므로 묶음 집계를 유지한다.
3. **구간 묶기**: L501~1500 은 100레벨 묶음, 레벨 단위는 L32~500.
